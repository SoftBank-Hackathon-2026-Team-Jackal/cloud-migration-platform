# Tasks: Provisioning

이 파일은 Provisioning 구현 티켓 **초안 인덱스**다. 각 티켓의 상세 수용 기준·Test Seam·검증 방법은 연결된 파일에 있다. 01은 사용자 요청(2026-11-03, #5)에 따라 내부 v1 입력 계약·로컬 검증·대상별 구성 예시를 완료했다. CP-01은 PR #10으로 main에 반영됐다. 02는 PR #12로 main에 반영됐다. 03은 PR #14로 main에 반영됐다. 04는 사용자 승인 후 실제 격리 K3s 검증을 완료했다. 04A는 PR #21로 main에 반영됐다. B-01(#17)의 공통 빌드 모듈은 PR #18로 main에 반영됐고 Workflow/Worker 연결은 후속 통합 범위다. 01A(#1)는 최신 v2 입력/Planning 검증과 로컬 검사를 완료했다. 04B(#23)는 v2 다중 리소스 공통 Chart 렌더를 완료했다. 05는 실제 AWS Provider 저장 Plan·민감정보 제거 Preview를 로컬 검증 경로에서 완료했고 운영 승인은 별도 선행 조건이다. 06은 ADC·프로젝트를 확인한 실제 GCP Provider 저장 Plan·Preview를 로컬 State에서 검증해 완료했고 운영 승인은 별도 선행 조건이다. 07(#34)은 테스트 DB/Temporal·가짜 executor 기준으로 Plan Revision 승인·실행 차단을 완료했고 실제 클라우드 승인은 08/10의 선행 조건이다. 08(#2)은 승인된 S3 State 저장 Plan을 실제 AWS에 Apply해 EKS `cmp-target-aws`를 준비했다(09를 위해 유지). 09(#37)는 그 EKS에서 DB·앱·ALB 배포와 READY 판정을 실제로 검증했다. 10(#2)은 승인된 S3 State 저장 Plan을 실제 GCP에 Apply해 GKE `cmp-target-gke`를 준비했다(11을 위해 유지, 노드 SA 로그·지표 IAM 바인딩은 후속). 11(#43)은 그 GKE에서 DB·앱·GCE Ingress 배포와 READY 판정을 실제로 검증했다. 13(#53)은 세 Provider의 실행 결과를 공통 `ProvisioningResult`로 정규화해 저장하고 Data/Traffic Migration 인계·사용자 요약 API를 제공한다. 14(#56)는 취소·Worker 종료·응답 유실·Agent 재연결을 실제 EKS·GKE·k3d에서 주입해 새 Revision 복구와 중복 방지를 확인했다. 12(#36)는 승인된 ON_PREM Plan의 Agent 운영 배포·READY 판정을 격리 k3d로 검증해 완료했고, 실행 dispatch 연결은 08 소유 계약을 따른다. 18(#98)은 Planning 입력 등록 → 대상별 Plan·Preview 게시(ON_PREM `WORKLOADS`, AWS/GCP `INFRASTRUCTURE`) → 승인자 Preview 조회 → `MigrationWorkflow` 승인 대기·실행 결과를 SQLite·로컬 ArtifactStore·실제 Helm 패키징·가짜 Terraform·Temporal 테스트 서버로 연결했다(실제 클라우드 Plan·서버 실행은 미검증). 22(#108)는 AWS/GCP 인프라 실행 결과로 별도 `WORKLOADS` Plan을 게시하고 승인 후 09·11 배포 → 13 인계까지 `MigrationWorkflow`를 이었다(가짜 Terraform·클러스터·Temporal 테스트 서버, 실제 클라우드 미실행). 사용자 지시에 따라 독립 티켓은 병렬 채팅에서 진행할 수 있다. 나머지 `DRAFT`는 사용자 검토 전 실제 구현을 시작하지 않는다. 상태는 `DRAFT → TODO → IN_PROGRESS → DONE`을 기본으로 하고, 선행 작업이나 결정이 막히면 `BLOCKED`로 기록한다. 검토 후 구현 전 GitHub Issue를 생성하거나 기존 Issue를 연결하고 아래 번호를 기록한다. `DONE`은 [개발 워크플로](../../docs/engineering/development-workflow.md)의 문서·테스트·리뷰 조건을 모두 충족한 경우에만 사용한다.

## 검토 및 결정 대기

- 사용자 검토에서 티켓의 크기·선행 관계·Test Seam 후보를 확정한다. 특히 `01`은 Analysis/Sandbox/Build의 실제 출력 계약과 Planning의 조합 책임을 먼저 맞춘다. 01의 내부 v1 구현과 공개 Planning/Adapter 테스트는 완료했다. 다른 팀의 실제 wire schema·참조 조회·실환경 연동은 후속 통합 범위이며, 내부 계약과의 변환 경계를 유지한다. 02/03은 렌더, 04는 로컬 폴링 Agent와 실제 격리 K3s 배포 검증 완료이며 05/06/07은 범위 검토 후 TODO다. 티켓별 착수 조건을 충족해야 한다. 나머지는 검토 전 DRAFT다.
- Preview/승인 유지, DB 승인 기록+Signal, 범용 Outbox 보류는 ADR-002로 결정했다. 07의 실제 API URL·필드·인증/권한·응답 계약은 담당자와 합의한다. ADR-002는 P0 범위 결정이며 ADR-001 스캐폴드 결정과 충돌하지 않는다.
- AWS/GCP 기존 네트워크 재사용 P0 제외와 중앙 S3 State+잠금은 결정했다. Node·신규 네트워크 Profile, Backend 실제 설정, 검증 계정/권한, Registry/Secret/TLS, Agent 완료 통지, 실패 후 정리는 관련 티켓의 결정 전제다.
- 티켓 이력은 유지한다. 요구사항이 바뀌면 영향받는 티켓과 SDD를 함께 갱신하고, 전체 티켓을 다시 생성하지 않는다.

## 온프레미스 외부 연결 (2026-11-05, 15~17)

사용자 결정: 중계 서버안(Route 53 → AWS 중계 서버의 Envoy → WireGuard → 온프레미스 K3s)을 전제로, Provisioning 범위는 외부 연결이 가능한 온프레미스 Agent까지다. 15는 Agent 상시 실행·설치, 16은 Agent·중계 서버 사이 키·설정·상태를 전달하는 플랫폼 API와 ON_PREM 결과 계약(터널 목적지), 17은 Agent 쪽 WireGuard 연결과 터널 주소 노출·검증이다. 중계 서버 내부(Envoy 라우팅·가중치, WireGuard 서버 peer 반영), DNS, 사용자 공인 주소, TLS, 롤백은 Traffic 담당이다. Traffic 담당 답변(2026-11-05): 중계 서버는 Agent 목록을 폴링, 터널 `10.200.0.0/24`·중계 서버 `.1`·MTU 1420, 중계 서버 EC2는 Traffic 담당이 생성, 온프레미스 앱 포트는 그대로 전달(16 T10~T13). UDP 차단 환경 대응은 아직 남은 확인 사항이다. Planning의 Plan 게시 연결(`onprem_preview`·`publish_plan_revision` 운영 호출)은 18(#98)이 세 대상으로 넓혀 구현했다. 웹 Agent 등록 화면은 범위 밖이다.

## 현재 진행 방식

사용자 지시에 따라 CP-01부터 한 티켓씩 순차 진행한다. 병렬 채팅을 만들거나 병렬 준비용 작업을 별도 수행하지 않는다. 문서는 관련 구현 이슈/PR에 함께 반영한다. 실제 공유 인터페이스는 [shared-contracts.md](shared-contracts.md)를 따른다.

## 이미지 흐름 변경 (ADR-003, Issue #17)

이전 내부 v1 Planning은 Build가 Sandbox를 참조하는 순서로 남는다. 새 제품 정책은 Build 선행·Sandbox 실행 Digest 검증·동일 Digest 배포다. [B-01](../../tickets/provisioning/b-01-image-build.md)은 공통 빌드 모듈이고 [01A](../../tickets/provisioning/01a-input-contract-v2.md)는 앱별 Build→Sandbox 출처·Digest의 **로컬 v2 Planning 검증**이다. 실제 S3/업무 DB 참조 조회, 다중 리소스 렌더, Workflow/Worker 연결과 승인 Plan 저장은 후속 범위다. 현재 01의 DONE은 **당시 v1 범위의 완료**이고 새 이미지 동일성 정책의 증거가 아니다. 04의 격리 Agent 배포 테스트도 수정 루프/Build 모듈의 완료 증거가 아니다.
