# Ticket 27 — 표준 테스트를 앱 API 모양에 맞추기 (DB 저장·재시작 후 유지 검증)

## 상태
DONE — PR #218 병합, Issue #199. **27-A**(표준 테스트의 쓰기 모양 설정·복구 대기·사유 코드·라우트 스캐너)는 구현 완료, 실제 k3d 확인 완료(2026-11-06, 후보 자동 선택은 제거함). **27-B**(Tester가 소스 근거로 테스트를 만듦)는 구현 완료(가짜 모델·가짜 서버로 검증). 미확인: 실제 Claude와 k3d에서 27-B 1회(비용 승인 후)

## 목적
지금 표준 쓰기·읽기 테스트는 앱이 `{id, value}`를 받고 `GET <경로>/<id>`로 돌려준다고 가정한다. 실제 Go 데모 앱은 `POST /api/messages`(`client_msg_id`·`author`·`body`, 성공 시 201과 저장된 메시지)와 `GET /api/messages?after=<id>`(목록)라서 이 테스트가 돌지 않았고, 실측(2026-11-06)에서는 헬스 테스트 하나뿐이었다. 설정만으로 앱의 쓰기 API 모양을 말해 주면 DB 저장과 DB 재시작 후 유지까지 검증하게 한다.

## 관련 요구사항
AV-012

## 선행 작업
Blocked by: 12, 22, 24 (병합됨). 27-A는 모델 호출이 없고 결정이 필요 없다. 27-B의 D-09 재정의는 사용자 결정으로 진행했다(아래 결정).

## 설계 방향 (2026-11-06)
앱의 쓰기 모양은 **설정**으로 받는다(덮어쓰기). 처음에는 후보 모양 중에서 Sandbox가 쓰기를 시험해 자동으로 고르는 단계(2층, `sbx_pick_shape`)도 만들어 실제 k3d에서 동작을 확인했지만 **제거했다**.
- 이유: 후보가 앱 하나(Go 데모 앱)뿐이라 일반성이 없고, Workflow 단계가 하나 늘어 부모와 배포 순서에 부담이 생긴다. 다른 앱은 어차피 후보에 없어 헬스만 돌게 된다.
- 일반화는 소스 근거를 쓰는 AI 테스트(아래 27-B)로 간다. 이 티켓의 러너 장치(모양 설정, 재전송 읽기, 복구 대기, 사유 코드)와 라우트 스캐너가 그 입력과 실행을 받는다.

## 작업 범위
- 포함
  - `AppApi`에 쓰기 모양 설정 추가: 쓰기 본문 틀(`write_body`, 실행마다 바뀌는 `{{run_id}}` 사용), 쓰기 성공 상태(`write_status`), 응답에서 서버가 만든 ID를 꺼낼 위치(`id_from_response`), 읽기 값 필드(`value_field`), 읽기 방식(`read_back`: 기본 `GET`, 새로 `REPEAT_WRITE`)
  - `REPEAT_WRITE`: 같은 쓰기를 한 번 더 보내 이미 저장된 행을 돌려받는다. 응답이 200이고 ID와 본문이 첫 쓰기와 같아야 통과. 앱의 중복 방지(같은 `client_msg_id` 재전송은 200과 저장된 행)를 읽기 검증으로 쓴다(목록에서 값으로 찾는 기능이 필요 없음)
  - 세 표준 테스트(헬스, DB 쓰기·읽기, DB 재시작 후 유지)가 새 모양을 따르게 하고, 설정이 없으면 지금 모양 그대로
  - `SandboxSettings`와 Sandbox 입력 조립이 위 설정을 `AppApi`로 넘김(고정 묶음 해시는 같은 설정이면 같음)
  - Go 코드의 HTTP 라우트 스캐너(`cmp_scanners.routes`)와 분석 문서의 `http_routes`(AI 테스트의 입력 후보로 둠)
  - 실제 k3d 확인에서 드러난 것: 앱은 DB 재시작 직후 "같은 ID로 재시도"하라는 503을 주므로 재시작 케이스가 복구를 기다려야 한다(`recover_seconds`). 또 테스트별 실패 사유 코드가 결과에 없어 원인을 알 수 없어서 결과에 싣는다.
  - 실행 안내(runbook)에 모양 설정 예시와 복구 대기 설명 추가, 실제 k3d 확인 기록
- 제외: 토큰 헤더가 필요한 쓰기 API(필요해지면 별도), 목록에서 값으로 항목 찾기, 후보 자동 선택(제거함), AI 테스트(27-B)

# 27-B — Tester가 소스 근거로 테스트를 만든다 (구현 완료, 실제 Claude·k3d 확인 대기)

## 목적
27-A는 앱의 쓰기 모양을 사람이 `--sandbox`에 적어야 하고, 적지 않은 앱은 헬스 테스트만 돈다. 또 AI 테스트는 1번 조건(원본 쪽 테스트 자원에서 먼저 통과, D-09) 때문에 원본 자원이 없으면 모델을 부르지도 못한다(`ORIGIN_UNAVAILABLE`). 앱마다 사람이 모양을 적지 않고, 원본 자원 없이도 쓸 수 있는 AI 테스트를 만든다.

## 설계 방향
테스트의 목적은 앱의 정확성이 아니라 **이전 후에도 같은 동작인가**(동등성)이다. 정답지(기대값)를 두 갈래로 얻는다. **기대값을 AI가 예측해서 쓰지 않는다**(구현을 따라 쓰는 편향과 틀린 예측을 막기 위해).

1. **속성 테스트(기대값이 테스트 안에서 정해짐):** 왕복(쓴 값 = 읽은 값), 재시작 후 유지, 멱등 재전송, 삭제 후 부재, 목록에 포함. 템플릿으로 고정하고 AI는 템플릿을 어느 경로·쓰기 모양에 묶을지만 고른다. 소스 근거(`파일:줄`)가 필수다.
2. **기록 기반 테스트(기대값이 앱 규칙에서 나옴):** AI는 읽기 전용 요청(입력)만 제출하고, 어떤 응답 필드가 매번 달라지는지 표시한다. 첫 Sandbox가 정상 기동한 직후 **코드가 원본인 기본 상태 앱**에 플랫폼이 요청을 보내 2xx 응답을 기록하고(골든), 기록을 단언으로 바꾼다. 묶음을 해시로 고정한 뒤에 Fixer가 개입한다(기존 조건 4와 같은 시점).

이 방식이 보장하는 것은 "기준 시점 이후 Fixer의 코드 수정이 동작을 바꾸지 않았다"까지이고, 기준 상태가 실제 AWS 원본과 같다는 것은 보장하지 않는다(범위 밖, 아래 제외). 원본 실행기가 있으면 추가 검증으로 쓸 수 있다.

## 작업 범위
- 포함
  - Tester 입력: 분석 문서의 `http_routes`(라우트와 위치)와 소스 조각을 읽는 읽기 전용 도구, `load_skill`. 지금은 표준 테스트가 쓰는 경로만 알려 준다.
  - `submit_tests`: 테스트마다 `evidence`(파일:줄)를 요구하고, 기록 기반 요청은 변동 필드 표시를 함께 낸다.
  - 근거 검사(기계): 파일·줄이 실제로 있고 해당 라우트·핸들러를 포함하는지 확인한다. 없으면 `UNVERIFIED`로 거절하고 사유를 남긴다.
  - 기록기: 요청 목록을 기준 상태 앱에 실행해 2xx 응답을 기록하고 마스킹 후 단언으로 바꾼다. 같은 요청을 두 번 기록해 다르면 거절한다. 기록 전에 테스트 데이터를 고정 시드로 초기화하고, 재생 때도 같은 시드를 쓴다.
  - `validate_tests`의 1번 조건을 바꾼다: 속성 테스트는 근거 검사, 기록 기반 테스트는 기록 성공으로 충족한다. 2번(필수 결과 단언), 3번(의존성을 끊으면 실패), 4번(수정 전에 고정)은 그대로다. 원본 실행기가 있으면 그것으로도 추가 확인한다.
  - 기록을 만들 수 없는 경우(코드 수정이 있어야만 정상 응답이 나옴)는 `BASELINE_UNAVAILABLE`로 공백을 남긴다.
  - 문서: spec AV-012(1번 조건 문구), plan D-09 행, runbook `ai_tests` 절과 `ORIGIN_UNAVAILABLE` 설명을 같은 PR에서 갱신한다. D-09 변경은 사용자 검토 후에만 문서에 반영한다.
- 제외: 이전 자체로 인한 동작 차이 검증(AWS 원본 자원 필요), 토큰 헤더가 필요한 쓰기 API와 멀티파트 업로드, 앱에 원래 있던 테스트 실행(`_test.go` 등 언어별), 코드 수정 승인 정책(별도 결정), Go 외 언어 라우트 스캐너, HTTPS 전용 앱·mTLS(지금 러너는 `kubectl proxy`의 HTTP 경로로만 앱에 닿는다. 서비스 이름에 스킴을 붙이는 방법은 실제 클러스터 확인이 필요해 후속으로 둔다), 비HTTP 앱과 헬스 경로의 근거 표시(후속 검토)

## 수용 기준
- [x] Tester에게 `http_routes`와 소스 조각(`get_snippet`)이 전달되고, 표준 테스트가 쓰지 않는 라우트도 후보가 된다. 비밀 파일(`.env`, 키·인증서)과 소스 밖 경로는 읽히지 않고 비밀 값은 마스킹된다.
- [x] 근거가 없거나 실제 소스와 맞지 않는 테스트는 거절되고 사유가 남는다(`NO_EVIDENCE`, `EVIDENCE_FILE_MISSING`, `EVIDENCE_LINE_MISSING`, `EVIDENCE_MISMATCH <경로>`). 원본 실행기가 있어도 소스가 있으면 근거를 확인한다.
- [x] 속성 테스트의 기대값은 그 테스트가 먼저 쓴 값(또는 앞 단계 응답에서 저장한 값)에서만 나온다. 다른 리터럴 기대값을 가진 자유 형식 테스트는 원본 실행기 없이는 `ORIGIN_UNAVAILABLE`이다. 모델은 `basis`를 `RECORDED`로 주장할 수 없다.
- [x] 기록 테스트의 기대값은 기준 상태 앱의 2xx 응답에서만 나오고, 변동 필드는 비교에서 빠지며, 같은 요청의 두 번 응답이 다르면 거절된다(`RECORD_UNSTABLE <필드>`). 비2xx, JSON 아님, 비어 있음, 너무 큼, 민감해 보이는 값, 도달 불가도 거절된다.

- [x] 의존성을 끊으면 실패해야 한다는 조건(3)은 그대로 적용된다. 의존성과 무관한 기록 읽기는 `PASSES_WITHOUT_DEPENDENCY`로 버려진다.
- [x] 원본 실행기가 없어도 `ORIGIN_UNAVAILABLE`로 막히지 않고 Tester가 호출된다(모델이 없으면 `LLM_NOT_CONFIGURED`). 쓰기 모양(`shapes`)은 왕복·재시작 후 유지 테스트가 되고, 모양이 건전하지 않으면(값 필드가 `value-{{run_id}}`가 아님, GET인데 ID가 없음 등) 제출이 되돌려진다.
- [x] 근거·기록 필드가 없는 기존 묶음은 바이트가 그대로다(해시 불변).
- [x] Workflow 변경 없음: `sbx_ai_tests` 활동 안의 변경이고 입력·결과 모양은 더해지기만 했다.

## 구현 메모
- 순서 문제: 묶음은 ID 순으로 실행된다. 기록한 읽기(`GET` 목록 등)는 기록 시점의 데이터(첫 apply 직후의 기준 상태)에서 나왔으므로 쓰기 테스트보다 먼저 돌아야 한다. 그래서 기록 테스트 ID는 `ai-0rec-<id>`(0은 글자보다 앞에 정렬)이고, 검증도 기록 테스트부터 하며, 검증이 쓴 데이터는 기준 상태로 되돌린다(되돌리는 일은 기존 `reset_test_data`).
- 알려진 한계: 라우트 스캐너는 Go 전용이다(다른 언어는 라우트 목록 없이 소스 조각만으로 읽는다). 앱이 재시작 때 시드를 다시 넣는 등 기준 상태가 흔들리는 앱은 기록이 불안정해 거절된다. 토큰 인증이 필요한 읽기는 기록하지 못한다.
