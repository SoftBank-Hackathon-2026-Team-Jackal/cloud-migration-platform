# ADR-011: Worker는 DB에 직접 붙지 않고 `kubectl exec`로 SQL을 실행하며, EKS 토큰은 Activity 사이에서 재사용한다

- Status: Accepted — 구현된 결정을 기록, 2026-11-08 (PR #351)
- Tracking: Issue #137, PR #138(DM-001 구현), PR #351(`EksSessionCache`), [티켓 02](../../tickets/data-migration/02-kubectl-psql-activities.md)
- 관련: [데이터 이전 명세](../../specs/data-migration/spec.md) DM-001·DM-008·DM-013·Q3, [구현 계획](../../specs/data-migration/plan.md), [ADR-010](./ADR-010.md)

## 배경

데이터 이전 Activity는 원본과 대상 DB에 SQL을 실행해야 한다. 명세 DM-001은 2026-11-05에 "Worker가 kubeconfig로 원본·대상 DB Pod 안에서 `psql`을 실행한다. DB를 Worker에 노출하지 않는다"고 정했다. PR #138이 이 방식으로 구현했다.

원본 DB는 EKS에 있다. `aws eks update-kubeconfig`가 만드는 kubeconfig는 exec 플러그인을 써서, `kubectl`을 부를 때마다 `aws eks get-token`이 다시 실행된다. PR #351 본문에 따르면 시연 기준 실행에서 데이터 이전 단계가 101초 걸렸고, 데모 Worker에서 EKS 호출 1회가 1.1~1.7초, 노트북 k3s 호출이 0.12초, 토큰을 미리 받아 둔 kubeconfig로는 EKS 호출이 0.10초였다.

## 결정

1. **SQL은 DB Pod 안에서 실행한다.** `KubectlDbPod`(`apps/worker/src/cmp_worker/activities/data_migration.py`)가 `kubectl exec -i -n <ns> <pod> -c <container> -- sh -c ...`로 `psql`을 부르고 SQL은 stdin으로 넘긴다. Pod 안에서는 유닉스 소켓으로 접속하므로 Worker는 DB 비밀번호가 필요 없다. 스키마 복사(`pg_dump --schema-only`)와 복원도 같은 경로다.
2. **복제 역할 비밀번호만 Worker가 만든다.** 구독자가 발행 DB에 접속할 때 쓰는 `cmp_repl` 역할의 비밀번호는 Worker가 만들어 구독자 쪽 Kubernetes Secret에 둔다(DM-013). 명령줄, Workflow 입력과 결과, 로그에는 남기지 않는다(DM-008).
3. **접근 방식별 연결은 `_runtime_for` 하나로 고른다.** `AWS_EKS`는 `EksSessionCache`, `GCP_GKE`는 `GcpCliRuntime.connect`, 그 밖에는 `DATA_MIGRATION_KUBECONFIG_DIR`의 kubeconfig 파일을 쓴다. 데이터 이전, 터널(`data_tunnel.py`), 전환(`data_cutover.py`) Activity가 모두 이 함수를 거친다.
4. **EKS 토큰은 프로세스 안에서 재사용한다(PR #351).** `EksSessionCache`는 `describe-cluster`로 받은 주소와 `get-token`으로 받은 토큰 하나로 정적 kubeconfig를 만든다. 토큰 만료 360초 전(`REFRESH_BEFORE_SECONDS`)까지 여러 Activity가 같이 쓴다. 키는 (클러스터 이름, 리전, `DATA_MIGRATION_AWS_PROFILE`)이다.
   - 파일은 0700 디렉터리 안의 0600 파일이고, 원자적으로 교체하며, 프로세스가 끝날 때 지운다.
   - 동시 호출은 잠금 하나로 묶어 갱신을 한 번만 한다.
   - `kubectl` 호출이 실패하면 캐시한 토큰을 버린다. 오류에 출력이 없어 토큰 거절을 구분할 수 없으므로, Activity 재시도가 새 토큰으로 시작하게 한다.
5. **범위:** 다른 Provisioning 경로(`CliRuntime.connect`)는 바꾸지 않았다. 그쪽은 `connect` 한 번 동안만 kubeconfig를 만들고 지우는 기존 규칙(`k8s_workloads_cli`)을 따른다. `GCP_GKE`와 kubeconfig 파일 경로에도 토큰 캐시를 두지 않았다.

## 이유

- DB를 Worker에 노출하지 않으므로 원본과 대상 DB에 새 입구나 방화벽 규칙이 필요 없다. Provisioning `database_probe`와 같은 방식이다(DM-001).
- 360초 여유는 가장 긴 단일 호출(`rollout status`, 최대 330초)이 시작할 때 받은 토큰으로 끝까지 가도록 잡은 값이다(PR #351, 코드 주석). 명세 Q3는 이 재사용 시간을 약 8분으로 적는다.
- PR #351은 핵심 경로의 EKS 호출 19회가 회당 약 0.1초가 되어 약 17~27초가 줄 것으로 추정했다.

## 결과와 위험

- Worker는 대상과 원본 클러스터에 Pod `exec`, Secret 생성과 교체 권한이 필요하다. 원본 EKS에는 데이터 전용 역할을 따로 둔다([데이터 티켓 12-source-write-role](../../tickets/data-migration/12-source-write-role.md)).
- 토큰은 Worker 임시 디렉터리의 파일에 최대 약 8분 남는다. Workflow 입력, 결과, 로그에는 들어가지 않는다.
- 토큰 거절과 다른 실패를 구분하지 못해, 실패할 때마다 다음 시도에서 토큰을 새로 받는다. PR #351 코드 주석은 이때 약 3초가 더 든다고 적는다.
- 전환 실행기는 `cmp-cutover` Pod 안에서 DB에 접속한다. Worker는 실행기를 부르고 결과 JSON만 받는다(ADR-010).

## 대안(검토했거나 남겨 둔 것)

- Worker가 DB에 직접 접속(포트 포워딩, 공개 입구): DM-001이 "DB를 Worker에 노출하지 않는다"로 배제했다.
- exec 플러그인 kubeconfig를 그대로 쓰기: PR #351 이전 방식이다. 호출마다 `get-token`이 돌아 느려서 바꿨다.
- 모든 Provisioning 경로에 같은 캐시 적용: PR #351 범위 밖으로 남겼다.
