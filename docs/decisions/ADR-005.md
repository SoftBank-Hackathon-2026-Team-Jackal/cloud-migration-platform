# ADR-005: 원본·대상 환경 연결 방식 (AWS 역할 위임, GCP 고정 프로젝트, 기준점 우선 범위)

- Status: Accepted — 사용자 결정, 2026-11-05
- 구현 추적: Issue #118, [티켓 23](../../tickets/provisioning/23-environment-connections.md), 요구사항 PROV-003·PROV-021·PROV-022

## 배경

분석 스펙은 "원본 접근·대상 환경 연결 발급"을 Provisioning 담당으로 둔다(`specs/analysis-verification/spec.md`). 지금까지 코드는 worker 호스트에 미리 설정한 이름 있는 AWS 프로필·gcloud configuration·ADC만 썼고, 웹 `/settings` 연결 관리 화면이 부를 API가 없었다.

## 결정

### AWS (원본·대상 공통): 키를 받지 않는다

- **방식:** 계정 간 `sts:AssumeRole` + 플랫폼이 연결마다 발급하는 External ID. 액세스 키·비밀 키·세션 토큰은 받지도 저장하지도 않는다. 플랫폼은 STS 임시 자격 증명만 메모리에서 쓴다.
- **사용자 절차:**
  1. 웹에서 연결을 만든다(`POST /connections`). 플랫폼이 External ID(`cmp-` + 32자리 hex, 연결마다 고유)와 CloudFormation 빠른 생성(Launch Stack) 링크를 돌려준다.
  2. 사용자는 자기 계정에서 링크로 스택을 만든다. 템플릿 매개변수는 플랫폼 주체 ARN과 External ID다.
  3. 스택 출력 `RoleArn`만 플랫폼에 등록한다(`PUT /connections/{id}/role`).
  4. 플랫폼이 확인한다(`POST /connections/{id}/verify`).
- **플랫폼 주체:** 플랫폼 자신의 AWS ID. 데모는 EC2 인스턴스 역할(티켓 21 `cmp-demo-instance`), 로컬은 개발용 이름 있는 프로필이다. 신뢰 정책은 이 주체 하나와 `sts:ExternalId` 조건뿐이다(`StringEquals`).
- **External ID:** 비밀이 아니지만(혼동된 대리인 방지용) 한 번만 발급하고 바꾸지 않는다. 운영자 상세 조회와 생성 응답에만 보이고 목록에는 나오지 않는다. Role ARN도 한 번만 등록한다. 바꾸려면 연결을 지우고 새로 만든다(새 External ID).
- **원본 역할(읽기 전용, `infra/connections/source-role.yaml`):** 분석 스캔이 실제로 부르는 API(`cmp_scanners.aws_infra.ALLOWED_OPERATIONS`)와 기준점 조회용 `eks:ListClusters`만 허용한다. 쓰기 동작은 없다. 테스트가 이 목록과 스캐너 목록의 일치를 강제한다. 분석 담당이 스캔 범위를 바꾸면 템플릿과 함께 바뀐다(분석 확인 대기).

  | 서비스 | 동작 |
  | --- | --- |
  | EKS | `eks:DescribeCluster`, `eks:ListClusters`(기준점 조회) |
  | EC2 | `ec2:DescribeVpcs`, `ec2:DescribeSubnets`, `ec2:DescribeRouteTables`, `ec2:DescribeSecurityGroups` |
  | ELBv2 | `elasticloadbalancing:DescribeLoadBalancers`, `DescribeListeners`, `DescribeTargetGroups` |
  | IAM | `iam:ListAttachedRolePolicies`, `ListRolePolicies`, `GetRolePolicy`, `GetPolicy`, `GetPolicyVersion` |
  | CloudTrail | `cloudtrail:LookupEvents` |

  `sts:GetCallerIdentity`는 권한이 필요 없다. 비밀 값 조회(Secrets Manager, SSM 파라미터 값, `kms:Decrypt`)는 없다.
- **대상 역할(EKS 신규 구축, `infra/connections/target-role.yaml`):** 생성 권한을 가진 별도 스택이다.
  - 읽기: `ec2:Describe*`, `eks:Describe*`/`List*`, `elasticloadbalancing:Describe*`, `iam:Get*`/`List*`.
  - 생성: VPC·서브넷·IGW·NAT·EIP·라우팅 테이블·보안 그룹·EKS 클러스터·노드 그룹·애드온. 요청 태그 `cmp:managed-by = terraform`(플랫폼 Terraform `local.tags`)이 있어야 한다(`aws:RequestTag`).
  - 변경·삭제: 같은 태그가 붙은 리소스만(`aws:ResourceTag`).
  - IAM 쓰기: 이름이 `ResourcePrefix`(기본 `cmp-`)로 시작하는 역할·정책과 EKS OIDC 공급자만. `iam:PassRole`은 그 역할을 `eks`/`ec2` 서비스에 넘길 때만.
  - 명시적 거부: IAM 사용자·액세스 키·로그인 프로필 생성, 연결 역할 자신의 정책·신뢰 변경.
  - 권한 경계(permission boundary)는 쓰지 않았다. Terraform이 만드는 역할에 경계를 붙이도록 바꿔야 해서 후속으로 둔다. 태그 조건을 평가하지 않는 일부 EC2 동작은 AWS 평가 규칙의 한계가 남는다.
- **`credential_ref` 해석(최종 결정): 생성된 AWS config 파일을 api·worker가 공유한다.**
  - 역할이 등록된 AWS 연결마다 이름 있는 프로필 `cmp-conn-<연결 hex>`를 만든다. 이 이름이 `credential_ref`이고, 분석 `get_session(credential_ref)`과 Provisioning `aws_profile`이 그대로 받는다.
  - 프로필 내용: `role_arn`, `external_id`, `source_profile = <플랫폼 프로필>`, `role_session_name`, `duration_seconds = 3600`, `region`.
  - API가 `connection_aws_config_file`에 원자적으로 다시 쓴다. 역할 등록·연결 삭제 때마다 DB 전체에서 다시 만든다. 앞부분에는 플랫폼 자신의 프로필 파일(`connection_aws_base_config_file`, 예: 데모 `credential_source = Ec2InstanceMetadata`)을 붙인다.
  - worker는 `AWS_CONFIG_FILE`을 이 파일로 둔다. 그러면 boto3·AWS CLI·Terraform AWS Provider가 SDK의 assume-role 공급자로 STS 임시 자격 증명을 받고 만료 때 스스로 갱신한다.
  - 파일에는 키가 없다(ARN·External ID·프로필 이름뿐).
  - 코드 수준 AssumeRole은 연결 확인과 기준점 조회에만 쓴다. 구조화된 오류 코드가 필요하고, Terraform·CLI 하위 프로세스에는 코드로 자격 증명을 넘길 수 없기 때문이다. 이 경로의 세션은 900초다.
- **Launch Stack 템플릿 호스팅:** CloudFormation 빠른 생성은 S3 HTTPS 템플릿 URL을 요구한다.
  - 저장소의 `infra/connections/*.yaml`을 플랫폼 계정의 S3 버킷에 공개 읽기 객체로 올린다(템플릿에 비밀이 없다). 그 접두어를 `connection_template_base_url`(예: `https://<bucket>.s3.<region>.amazonaws.com/connections/v1`)로 설정한다.
  - 템플릿을 바꾸면 경로 버전(`v2`)을 올린다. 이미 만든 스택의 내용이 바뀌지 않게 하기 위해서다.
  - 설정이 없으면 `launch_stack_url`은 `null`이고, 사용자는 템플릿 파일로 직접 스택을 만든다.
  - 버킷 생성·업로드는 승인이 필요한 원격 작업이다.

### GCP

- **데모:** 플랫폼 프로젝트 하나로 고정한다(`connection_gcp_project_id`). 다른 프로젝트는 생성 단계에서 거절한다.
- **연결 기록:** `GCP_TARGET` 연결은 프로젝트 ID·리전·예상 ADC 주체를 저장한다.
- **확인:** 기존 Planning의 ADC 주체 확인(`cmp_providers.gcp_preview.verify_adc_principal`, tokeninfo의 email 비교)을 그대로 쓴다. 실패 코드도 같다(`ADC_PRINCIPAL_MISMATCH`, `ADC_UNAVAILABLE`, `ADC_CHECK_FAILED`, `ADC_SOURCE_UNSUPPORTED`).
- **서비스 계정 키 JSON은 받지 않는다.**
- **목표 방식(설계만, 구현 후속): Workload Identity Federation.**
  - 사용자 프로젝트에 AWS 공급자를 둔 Workload Identity Pool을 만들고, 플랫폼 AWS 주체(인스턴스 역할 ARN)를 속성 조건으로 신뢰한다.
  - 그 외부 ID에 사용자 서비스 계정의 `roles/iam.workloadIdentityUser`를 준다.
  - 플랫폼은 AWS 서명 요청을 STS 토큰으로 교환하고 서비스 계정을 가장한다(외부 계정 credential config. 키가 아니라 교환 규칙만 담는다).
  - 연결 기록에는 pool/provider 리소스 이름과 서비스 계정 이메일만 남는다. 이렇게 하면 AWS와 같은 "플랫폼 주체 하나가 사용자 측에서 위임받는" 모델이 된다.

### 범위: 기준점 우선(anchor-first)

- 계정 전체를 스캔하지 않는다. 플랫폼은 기준점 조회만 제공한다. 원본 연결에서 리전을 고르면 그 리전의 EKS 클러스터 목록을 준다(`GET /connections/{id}/eks-clusters?region=`). 연결 확인도 등록 리전의 클러스터 목록을 함께 준다.
- 기준점(리전·클러스터)에서 참조를 따라가 스캔하고 범위를 확정하는 일은 **분석 담당**이다. 근거 종류는 `Evidence.kind`: CODE/MANIFEST/CLOUD_RESOURCE/IAM_POLICY/CLOUDTRAIL/CONFIG. 플랫폼은 선택된 기준점을 받아 넘기는 쪽까지만 맡는다.
- 네임스페이스·워크로드 목록은 IAM 읽기 권한만으로는 볼 수 없다. Kubernetes API 접근, 즉 EKS access entry가 필요하므로 후속으로 둔다.
- 선택 사항(후속): 분석 세션을 AssumeRole 세션 정책으로 고른 리전·클러스터에 좁힐 수 있다. 세션 정책에서 `aws:RequestedRegion` 조건을 쓰고, `eks:DescribeCluster` 리소스를 해당 클러스터 ARN으로 둔다. 세션 정책은 역할 권한을 더 줄일 뿐 넓히지 않는다.

### API와 보안 경계

- `/connections*`와 `/agent-admin/agents`는 운영자 키(`X-Enrollment-Admin-Key`, Agent 관리와 같은 키)로만 호출한다. 웹 BFF가 서버 측에서 부르므로 CORS는 열지 않는다.
- 확인 실패는 HTTP 200 + `status: FAILED` + 고정 코드로 남긴다: `ROLE_NOT_SET`, `ASSUME_ROLE_DENIED`, `ASSUME_ROLE_FAILED`, `PLATFORM_CREDENTIALS_UNAVAILABLE`, `IDENTITY_CHECK_FAILED`, `ACCOUNT_MISMATCH`, `EKS_LIST_DENIED`, `EKS_LIST_FAILED`, GCP 코드. AWS·Google 원문 메시지는 남기지 않는다.
- **`EXTERNAL_ID_MISMATCH`는 만들지 않는다.** AWS는 External ID가 틀린 경우와 신뢰 정책이 없는 경우를 같은 `AccessDenied`로 응답해, 밖에서는 둘을 구별할 수 없다. 둘 다 `ASSUME_ROLE_DENIED`이고, 화면은 "스택 매개변수의 External ID와 플랫폼 주체를 확인"하라고 안내한다.
- DB에는 Role ARN·External ID·계정 ID·주체 ARN·확인 시각·코드만 저장한다. 임시 자격 증명은 DB·응답·로그·Temporal 이력 어디에도 없다. 확인은 API 프로세스 안에서 끝나고 Workflow를 거치지 않는다.
- 422 응답은 입력값을 되돌려 보내지 않는다. 사용자가 실수로 키를 붙여 넣어도 응답에 다시 나타나지 않는다.

## 기각한 대안

| 대안 | 기각 이유 |
| --- | --- |
| IAM 사용자 액세스 키 입력 | 장기 비밀을 플랫폼이 보관·회전·폐기해야 한다. 유출되면 사용자 계정이 무기한 노출된다. 사용자가 권한을 좁혔는지 플랫폼이 강제할 수 없다. AWS도 제3자 접근에 권장하지 않는다(External ID 역할 위임 권장) |
| External ID 없는 역할 위임 | 다른 고객이 같은 플랫폼에 남의 Role ARN을 등록하는 혼동된 대리인 공격에 열린다 |
| 사용자가 External ID를 고름 | 고유성·예측 불가능성을 보장할 수 없다. 플랫폼 발급만 허용한다 |
| GCP 서비스 계정 키 JSON 업로드 | 장기 비밀이고, 키 생성이 조직 정책으로 막힌 곳이 많다. 유출 시 회수가 늦다. 데모는 고정 프로젝트 ADC, 목표는 WIF |
| 계정 전체 자동 스캔 | 비용·시간·권한이 과하다. 관련 없는 리소스를 근거로 오인할 수 있다. 기준점 우선으로 분석 담당이 범위를 확정한다 |
| 코드 수준 AssumeRole만(프로필 파일 없음) | Terraform·AWS CLI 하위 프로세스(Provisioning Plan/Apply)에 자격 증명을 넘기려면 임시 키를 환경 변수로 줘야 한다. 그러면 Temporal 이력·로그 노출 위험이 커지고 갱신도 안 된다. 기존 `credential_ref`/`aws_profile` 경로가 변경 없이 동작하지도 않는다 |

## 남는 일(후속·승인 필요)

- 데모 인스턴스 역할에 `sts:AssumeRole` 허용을 추가해야 한다. 리소스는 `arn:aws:iam::*:role/*`이고, 조건으로 `aws:ResourceTag/cmp:managed-by = cloud-migration-platform`을 검토한다. 데모 compose에서 API 컨테이너에 플랫폼 프로필·생성 config 경로를 공유하고, worker `AWS_CONFIG_FILE`이 생성 파일을 가리켜야 한다. 템플릿 S3 버킷이 필요하다. 셋 다 원격 변경이라 사용자 승인 대상이다.
- 다른 계정 대상에 Apply할 때 Terraform S3 backend(플랫폼 계정 State 버킷)가 대상 프로필로 접근하게 된다. backend에는 플랫폼 프로필(`-backend-config=profile=`)을 따로 줘야 한다. AWS Apply 경로를 바꾸는 일이라 후속이다.
- `MigrationRequest`에 `source_connection_id`/`target_connection_id`를 실을지는 Migration 담당과 합의할 후속 제안이다(티켓 23).
- 실제 계정에서 스택 생성 → 등록 → 확인 → 분석 스캔·Plan을 실행하는 검증은 미검증이며 사용자 승인 후 진행한다.

## 후속 메모 (2026-11-06, [티켓 46](../../tickets/provisioning/46-connection-credentials.md), Issue #181)

결정 자체는 바꾸지 않았다. 위 "`credential_ref` 해석"과 "남는 일"을 다음처럼 구현·구체화했다.

- **Provisioning이 연결을 쓰는 방법:** AWS Plan 입력의 기존 `credential_ref`(`VersionRef`)의 `id`가 연결 ID(`conn-<12 hex>`)면 그 대상 연결이다. 프로필 `cmp-conn-<12 hex>`로 Terraform provider·`aws sts`·`aws eks`·kubectl을 실행한다. Apply와 AWS 워크로드는 **승인된 Spec**에 고정된 값을 다시 해석한다. 연결 ID가 아니면 지금처럼 worker 고정 프로필(데모 같은 계정)이다. 해석 함수는 `cmp_providers.aws_credentials.resolve_aws_profiles`다.
- **State backend:** `-backend-config=profile=<플랫폼 프로필>`을 항상 따로 준다(남는 일 두 번째 항목 해결).
- **Plan 전 확인:** 연결이 `AWS_TARGET`·`CONNECTED`이고 확인된 계정이 Plan의 `account_id`와 같아야 한다(`TARGET_CONNECTION_*` 코드). 연결 경로의 `cluster_name`은 `cmp-`로 시작해야 한다(대상 템플릿 IAM 접두어 고정).
- **플랫폼 주체:** 위 "플랫폼 주체 = 인스턴스 역할"을 **이름 고정 역할 `cmp-platform-connector`**로 바꿨다. 인스턴스 역할이 이 역할을 Assume하고, 이 역할만 사용자 역할(`role/cmp-*`, 태그 `cmp:managed-by = cloud-migration-platform`, External ID 필수)을 Assume한다. 인스턴스 역할이 다시 만들어져도 사용자 신뢰가 끊기지 않는다. 별도 스택 `cmp-demo-connector`라 컨트롤 플레인 스택을 갱신하지 않는다. 생성 프로필은 두 번 연쇄된다(세션 1시간 한도 안).
- **사용자 역할 이름:** 템플릿이 `cmp-<source|target>-<External ID hex>`로 고정한다(위 Assume 범위와 맞춤).
- **템플릿 호스팅:** 같은 스택의 버킷 `connections/v1/`. 연결 생성·상세 응답에 `platform_principal_arn`을 추가했다(링크 없이 파일로 만드는 사용자용).
- **공유 파일:** api가 시작 때도 DB에서 생성 파일을 다시 쓴다. 데모는 `/opt/cmp/data/aws-connections/config`(api 쓰기, worker 읽기).
