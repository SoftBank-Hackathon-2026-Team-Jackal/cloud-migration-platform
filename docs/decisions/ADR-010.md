# ADR-010: 데이터 이전은 PostgreSQL 논리 복제로 하고, 전환은 원본 쪽 PgBouncer로 한다

- Status: Accepted — 구현된 결정을 기록, 2026-11-08 (PR #138)
- Tracking: Issue #137, PR #138, [티켓 02](../../tickets/data-migration/02-kubectl-psql-activities.md), [04](../../tickets/data-migration/04-switchover-rollback.md), [05](../../tickets/data-migration/05-workflow-wiring.md), [06](../../tickets/data-migration/06-pgbouncer-wireguard-path.md), [07](../../tickets/data-migration/07-cutover-approval-events.md)
- 관련: [데이터 이전 명세](../../specs/data-migration/spec.md) DM-005·DM-007·DM-010·DM-012~DM-014, [구현 계획](../../specs/data-migration/plan.md), [ADR-006](./ADR-006.md)(DB 게이트), [ADR-007](./ADR-007.md)(ON_PREM 복제 경로)

## 배경

아키텍처 개요는 DB 데이터 이전을 "PostgreSQL Logical Replication, 세부 절차 미정"으로 남겼다. 데이터 이전 명세(DM-010, DM-011)는 쓰기 중단 장치와 복제 경로를 2026-11-05에 정했고, PR #138이 예선·본선 PoC(`poc/cdc`)의 논리 복제와 빠른 전환·롤백을 플랫폼 Activity와 `DataMigrationWorkflow`로 옮겼다. 이 결정은 명세에만 있고 ADR이 없었다.

## 결정

1. **초기 복사와 CDC는 논리 복제로 한다.** `dm_copy_schema`가 `pg_dump --schema-only`로 스키마를 옮기고, `dm_subscribe`가 원본 publication과 대상 subscription(`copy_data=true`)을 만든다. 이름은 migration_id와 방향으로 고정한다(DM-004).
2. **감시는 짧은 Activity를 반복한다.** `dm_sample`, `dm_readiness`를 Workflow 타이머 간격으로 부르고, 단계는 `schema → copy → catchup → streaming`이다(DM-005). 전환은 가장 긴 트랜잭션 200ms 이하, 잠금 대기 0건, 슬롯 지연 1 MiB 이하일 때만 한다(DM-006).
3. **쓰기 중단 장치는 원본 클러스터의 PgBouncer다(DM-010).** `dm_install_cutover`가 원본 앱 Namespace에 `cmp-cutover` Pod(컨테이너 `pgbouncer`, `runner`)와 Service `cmp-pgbouncer:6432`를 둔다. 처음 연결 대상은 원본 DB다.
4. **앱 연결은 한 번만 바꾼다.** `dm_route_app`이 앱 Secret의 `DATABASE_URL` 호스트와 포트만 PgBouncer로 바꾸고 Deployment를 재시작한다. 이미 바꿨으면 재실행 때 건너뛴다. 재시작 뒤에는 옛 Pod가 모두 사라질 때까지 기다린다(DM-014).
5. **쓰기 주체 전환은 Pod 안의 실행기가 한 번에 한다.** `dm_switchover`가 `infra/data-migration/cutover/switchover.py`를 stdin JSON 설정으로 부른다. 순서는 `PAUSE` → 마지막 변경 도착 확인 → 연결 대상 변경(`databases.ini` 교체와 `RELOAD`) → `RESUME`이다. 앱 연결은 끊지 않는다. 직접 붙은 세션이 있으면 `DIRECT_CLIENTS`로 거절한다. 성공하면 `cmp-cutover` Secret의 연결 대상도 새 주 DB로 바꾼다.
6. **롤백은 역방향 복제로 한다.** 전환할 때 옛 주 DB가 새 주 DB를 구독하는 역방향 복제를 준비하고(`origin = none`), 롤백은 같은 Activity를 `direction: reverse`로 다시 부른다. 대상 DB가 발행자가 되도록 `wal_level`이 logical이 아니면 준비 단계에서 바꾸고 Pod를 한 번 재시작한다(DM-012).
7. **DB 전환과 트래픽 전환은 나눈다(DM-007).** `DataMigrationWorkflow`의 `db_gate` Query가 `writer`와 `reverse_replication_ok`를 내고, 부모 `MigrationWorkflow.db_gate_ok()`가 이를 Traffic에 넘긴다. Traffic은 `require_db_gate`가 켜져 있으면 이 값이 `True`가 아닐 때 100% 단계를 막는다(ADR-006 결정 5). 부모는 DB가 대상으로 전환될 때까지 기다린 뒤 트래픽 단계로 간다(티켓 05).
8. 전환 신호 `switchover`는 웹 두 번째 승인(`POST /migrations/{id}/approve?gate=cutover`)이 보낸다(티켓 07). 전환은 한 번만 시도하고, 거절되면 쓰기 주체를 그대로 둔다.

## 이유

- 전환은 밀리초 단위라 SQL마다 `kubectl exec`를 하면 쓰기 중단이 수백 ms가 된다(티켓 04). 그래서 실행기가 Pod 안에서 접속을 유지한 채 한 번에 돈다.
- PgBouncer가 연결 대상만 바꾸므로 앱은 전환과 롤백 때 재시작하지 않는다. 앱 재시작은 연결을 PgBouncer로 바꿀 때 한 번뿐이다.
- 시험 결과(티켓 04): data-lab(k3d 두 개, 초당 약 50건 쓰기)에서 쓰기 중단 4~7ms, EKS 안 Namespace 사이에서 전환과 롤백 각 21ms, EKS에서 GKE로 WireGuard를 거친 시험에서 전환 110ms, 롤백 56ms였다. 모두 체크섬이 일치했고 커밋된 쓰기 누락이 0건이었다.
- 물리 복사(`pg_createsubscriber`)는 PG17 전용이고 플랫폼 대상 DB가 PostgreSQL 16이라 쓰지 않는다(명세 범위 밖).

## 결과와 위험

- 원본 앱은 PgBouncer로 바꿀 때 한 번 재시작된다. 종료 중인 옛 Pod가 원본 DB에 직접 쓰면 그 쓰기가 사라질 수 있다. EKS 첫 시험에서 594건이 새 주 DB에 없었고, `DIRECT_CLIENTS` 검사와 옛 Pod 대기로 고쳤다(DM-014).
- `cmp-cutover` Pod를 다시 만들면 앱의 PgBouncer 연결이 끊긴다. 실습에서 재시작 한 번에 앱 오류 8~9건이 났다(티켓 04).
- 새 주 DB의 시퀀스는 옛 주 값에 10000을 더해 미리 올린다. 스키마 복사 뒤 DDL은 금지다(티켓 04).
- PgBouncer 설치는 사전 점검 직후 시작한다(`data-early-cutover-install-v1`). 준비나 복사 중에 실패하면 원본 Namespace에 `cmp-cutover` 리소스가 남을 수 있고 자동 제거는 없다(티켓 05).
- 원본 앱의 Egress NetworkPolicy가 PgBouncer 연결을 막을 수 있다. 이 처리는 [ADR-012](./ADR-012.md)에 기록한다.
- 트래픽만 원본으로 되돌려도 데이터가 복구되지는 않는다. DB 롤백은 `rollback` 신호로 따로 해야 한다(ADR-006 한계).
- ON_PREM 대상에서 전체 복제, 전환, 롤백을 실측했는지는 확인하지 않음(구현 계획은 별도 검증이 필요하다고 적는다).

## 대안(검토했거나 남겨 둔 것)

- 쓰기 중단 장치와 복제 경로의 다른 후보: 명세 Q1, Q2는 PgBouncer와 WireGuard로 해결했다고만 적고, 비교한 후보는 적지 않았다. 확인하지 않음.
- 물리 복사(`pg_createsubscriber`): PostgreSQL 16 대상이라 쓰지 않는다.
- ON_PREM 복제 경로의 1안(Agent 터널, 중계 서버, VPC 피어링): ADR-007이 대안으로 남겼다.
