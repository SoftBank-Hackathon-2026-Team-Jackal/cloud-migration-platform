# ADR-009: 플랫폼 스택은 FastAPI API와 Temporal Worker로 한다

- Status: Accepted — 구현된 결정을 기록, 2026-11-08 (PR #30, #33)
- Tracking: Issue #27(PR #30), Issue #32(PR #33), [티켓 Q-01](../../tickets/analysis-verification/q-01-sandbox-queue.md)
- 관련: [ADR-001](./ADR-001.md)(Temporal 학습 스캐폴드), [ADR-002](./ADR-002.md), [ADR-006](./ADR-006.md)(릴레이 워커), [아키텍처 개요](../architecture/overview.md), [Temporal 실행 흐름](../architecture/temporal-flow.md), [개발 절차](../engineering/development-workflow.md)

## 배경

ADR-001은 Temporal을 익히기 위한 스캐폴드 결정이고, 실제 플랫폼 스택 채택을 기록하지 않았다. ADR-002도 자신을 전체 플랫폼 스택 채택 ADR로 쓰지 않는다고 적었다. `docs/engineering/development-workflow.md`는 "a full FastAPI + Temporal adoption ADR has not yet been assigned"라고 적어 이 공백을 남겼다. 그사이 코드는 FastAPI API와 Temporal Worker 구성으로 구현됐다. 이 ADR은 ADR-001을 다시 쓰지 않고, 이미 구현된 실제 스택 채택을 따로 기록한다.

## 결정

1. 외부 HTTP 입구는 FastAPI 앱 `cmp_api.main:app`(`apps/api/src/cmp_api`) 하나다. 이전 시작, 상태 조회, 승인, 취소, SSE(`text/event-stream`, `routes/migrations.py`)를 맡는다. 오래 걸리는 작업은 HTTP 요청 안에서 실행하지 않고 Temporal Workflow를 시작한다.
2. 장시간 작업은 Temporal Python SDK(`temporalio`)로 실행한다. Workflow와 Activity는 `apps/worker/src/cmp_worker`에 있다.
3. Task Queue 이름은 `cmp_contracts.queues`에 모아 API와 Worker가 같이 쓴다.
   - `migration`(`WORKFLOW_QUEUE`): Workflow 전용. `MigrationWorkflow`, `ProvisioningApprovalWorkflow`, `AnalysisWorkflow`, `SandboxVerificationWorkflow`, `TrafficShiftWorkflow`, `DataMigrationWorkflow` 등을 등록한다(`workers/migration.py`).
   - Activity 전용 큐: `analysis`, `sandbox`, `build`, `provisioning`, `migration-activities`(`MIGRATION_QUEUE`, 데이터·트래픽 Activity).
   - 중계 서버 호스트의 릴레이 워커(`workers/relay.py`)는 요청의 `relay_queue`로 이름을 받는 별도 큐에서 트래픽과 그림자 리허설 Activity만 처리한다.
4. API는 실행 중인 Workflow에 Signal로 입력을 보내고 Query로 상태를 읽는다. 예: `approve`, `switchover`, `request_cancel` Signal과 `status` Query(`routes/migrations.py`), 승인 Signal `approval_recorded`(`APPROVAL_SIGNAL`), 분석 검토 Query `review_state`, Cloud 정리 Signal `confirm_destroy`.
5. 패키지 경계: 공통 로직은 `packages/*`(`cmp_contracts`, `cmp_providers`, `cmp_scanners`, `cmp_agents`, `cmp_testsuite`, `cmp_traffic`, `cmp_data`)에 둔다. 2026-11-08에 확인했을 때 `packages/` 아래 코드에는 `temporalio`, `cmp_api`, `cmp_worker`를 import하는 줄이 없다. Temporal과 외부 I/O 연결은 `apps/worker`가 맡는다. 모든 패키지는 루트 `pyproject.toml` 한 프로젝트로 설치한다.
6. 데모 배포는 단일 EC2의 Docker Compose(`infra/demo/compose.yaml`)다. FastAPI, Worker, Temporal(`temporalio/auto-setup:1.29.1`), Temporal UI, 업무 PostgreSQL, Temporal PostgreSQL을 함께 띄운다. Worker 컨테이너는 기본으로 `python -m cmp_worker.workers.run_all`을 실행해 한 프로세스에서 모든 큐를 처리한다. 큐 하나만 띄우는 진입점(`workers/run.py --queue`)도 있다.

## 이유

- 분석, 빌드, Sandbox 검증, 승인 대기, Provisioning, 데이터 복제, 트래픽 전환은 한 HTTP 요청 안에서 끝나지 않는다. 실행 이력, 재시도, 승인 대기와 재개는 Temporal이 맡는다(`temporal-flow.md` §2).
- Activity 큐를 나누면 같은 코드를 한 프로세스로도, 큐별 프로세스로도 띄울 수 있다. 중계 서버처럼 특정 호스트에서만 해야 하는 일은 그 호스트의 큐로 보낸다(ADR-006).
- 판단 로직을 `packages/*`에 두면 Temporal 없이 단위 시험할 수 있다.
- PR #30은 배포된 Temporal에서 승인 대기와 재개 스캐폴드 smoke(`scaffold_complete`)를 확인했다. PR #33은 Temporal 시험 환경에서 Sandbox 큐의 Task 전달과 단독·전체 Worker 등록을 확인했다.

## 결과와 위험

- 데모는 단일 호스트이며 고가용성 구성이 아니다(`infra/demo/README.md`).
- Worker를 재시작하면 실행 중인 Activity가 취소된다. 배포 스크립트는 `Running` Workflow가 있으면 배포를 멈추거나 Worker 교체를 건너뛴다(`infra/demo/README.md`).
- `apps/worker`는 `cmp_api`의 DB 세션과 이벤트 저장소를 import한다(예: `workers/run_all.py`의 `DbEventEmitter`). 의존 방향은 Worker → API 한쪽뿐이고, 반대 방향(`apps/api`가 `cmp_worker`를 import)은 없다.
- 아키텍처 문서(`overview.md`, `temporal-flow.md`)에는 "Task Queue 이름을 확정하지 않는다", "로컬 스캐폴드" 같은 스캐폴드 시기의 문장이 있다. 실제 스택은 이 ADR을 기준으로 본다.

## 대안(검토했거나 남겨 둔 것)

- 별도 작업 큐(Redis, Celery, Kafka): 아키텍처 개요가 확정 스택에서 뺐다.
- 큐 또는 Worker 직접 조정, Kubernetes Job: ADR-001이 스캐폴드 단계에서 고르지 않았다.
- 운영용 Temporal 구성(별도 클러스터, 클라우드 서비스): 데모 범위 밖이라 쓰지 않았다.
