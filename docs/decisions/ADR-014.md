# ADR-014: 시연 플랫폼은 단일 EC2의 Docker Compose로 운영하고, main 커밋만 결정적으로 배포한다

- Status: Accepted — 구현된 결정을 기록, 2026-11-08 (PR #30, PR #347)
- Tracking: Issue #27(단일 EC2 배포), PR #347(main 전용·잠금 대기·실행 중 이전 보호)
- 관련: [infra/demo/README.md](../../infra/demo/README.md), [`.github/workflows/deploy-demo.yml`](../../.github/workflows/deploy-demo.yml), [`infra/demo/activate.sh`](../../infra/demo/activate.sh), [`infra/demo/release.sh`](../../infra/demo/release.sh), [ADR-009](./ADR-009.md)(플랫폼 스택)

## 배경

대회 시연에는 API, Worker, Temporal, 업무 DB, Temporal DB, Temporal UI, 웹, 공개 HTTPS 입구가 함께 떠 있어야 한다. 팀원 여러 명이 같은 날 여러 번 배포하고, 시연 리허설도 같은 서버에서 돌린다. 이때 생긴 문제는 두 가지다.

1. 배포가 Worker를 다시 시작하면 실행 중인 Temporal Activity가 취소된다. 시연 이전이 중간에 끊겨 처음부터 다시 해야 한다.
2. 작업 브랜치에서 로컬로 배포하면 서버가 어떤 코드로 동작하는지 main 기록만으로는 알 수 없다. 같은 커밋을 배포해도 결과가 달라질 수 있다.

## 결정

### 실행 형태

- 서울 리전 단일 EC2 한 대에 Docker Compose로 `platform-db`, `temporal-db`, `temporal`, `temporal-ui`, `api`, `worker`, `web`, `edge`를 실행한다(`infra/demo/compose.yaml`). 서비스는 `restart: unless-stopped`로 둔다.
- 인스턴스 유형은 `CMP_DEMO_INSTANCE_TYPE`으로 정한다. 2026-11-07 본선 시연에 맞춰 `t3.large`에서 `m7i.2xlarge`(8 vCPU, 32 GiB)로 올렸고, 루트 EBS는 암호화된 80 GiB다.
- 운영 접속은 SSM으로만 한다. Security Group 인바운드는 HTTPS 443 하나다.
- S3 버킷은 Terraform State·잠금용과 배포 소스 전달용으로 나눈다.
- DB 비밀번호와 Agent 운영자 키는 처음 기동할 때 `/opt/cmp/.env`에 만들고, 재배포할 때 보존한다.

### 배포 경로

- 평소에는 GitHub Actions `Deploy demo`를 main에서 수동으로 실행한다. 이 워크플로는 GitHub OIDC로 배포 전용 역할을 잠시 사용하고, `revision` 입력으로 이전 main 커밋을 다시 배포할 수 있다. 같은 워크플로가 중계 서버 라이브러리(`infra/relay/sync-lib.sh`)도 같은 커밋으로 맞춘다.
- `release.sh`는 커밋의 `git archive`를 S3에 올리고, SSM으로 서버의 `activate.sh`를 실행한다. 로컬 AWS 자격 증명을 서버로 복사하지 않는다.

### 결정성을 지키는 규칙 (PR #347)

1. **main 커밋만 배포한다.** 로컬에서 실행해도 `origin/main`에 들어간 커밋만 받는다. 서버에서 실행하는 `activate.sh`는 배포할 커밋이 아니라 main에 있는 것을 올린다. 작업 브랜치가 서버의 배포 절차를 바꾸지 못하게 하기 위해서다. `CMP_ALLOW_UNMERGED=1`은 로컬 전용 예외다.
2. **실행 중인 Workflow가 있으면 배포하지 않는다.** `activate.sh`는 Temporal UI의 HTTP API(서버 내부 `127.0.0.1:8080`)에 `ExecutionStatus="Running"`을 조회한다. 결과가 하나라도 있으면 아무것도 바꾸지 않고 Workflow ID를 출력한 뒤 실패한다. Temporal UI 컨테이너는 떠 있는데 API가 응답하지 않으면, 실행 중인지 알 수 없으므로 역시 거절한다.
3. **강제 배포는 명시적으로만 한다.** 워크플로 입력 `force`(기본 false)나 로컬 `CMP_DEPLOY_FORCE=1`을 줄 때만 위 확인을 건너뛴다. 이때 실행 중인 이전은 취소된다.
4. **배포는 서로 기다린다.** `activate.sh`와 `release-web.sh`는 `/opt/cmp/deploy.lock`을 최대 15분 기다린다. GitHub Actions에서도 `concurrency` 그룹 하나로 배포를 순서대로 실행한다.
5. **실패하면 이전 리비전으로 돌아간다.** 새 리비전의 시작 확인이 실패하면 롤백하기 전에 로그를 `failed-deploy-<rev>-<시각>.log`로 남기고(최근 5개), 서버에 보관한 이전 리비전을 다시 시작한다.
6. **모든 시도를 한 줄로 남긴다.** `deploy-history.log`에는 시각, 플랫폼 리비전, 웹 리비전, `.env`·`web.env`의 sha256 앞 12자, 결과를 적는다. 값이 아니라 지문만 남기므로, 지문이 바뀌었다면 코드가 아니라 서버 설정이 바뀌었다는 뜻이다.
7. **공개 입구까지 확인한다.** `CMP_PUBLIC_HOST`가 있으면 `start.sh`는 `https://<host>/`가 5xx 없이 응답해야 성공으로 본다.

## 이유

- **비용과 준비 시간.** 대회 기간에 필요한 것은 시연 하나를 안정적으로 돌리는 것이다. EKS나 관리형 Temporal을 따로 두면 비용이 늘고, 준비하는 데 걸리는 시간도 늘어난다. 단일 호스트는 고장 지점이 하나지만, 문제가 생겼을 때 원인을 찾을 곳도 하나다.
- **시연 보호가 배포 편의보다 중요하다.** 시연 이전 한 번은 몇 분이 걸린다. 그 사이에 다른 팀원이 배포하면 이전이 취소되고 처음부터 다시 해야 한다. 실행 중인 Workflow를 확인하면 이런 사고를 배포 단계에서 막을 수 있다.
- **"서버에 무엇이 돌고 있는가"를 main 기록으로 답할 수 있다.** main 커밋만 배포하므로 `/opt/cmp/current-revision`의 값은 언제나 main 기록에 있는 커밋이다.
- **Temporal UI API를 확인 수단으로 쓴다.** 서버에는 이미 Temporal UI가 떠 있고, 별도 CLI를 설치하지 않아도 내부 주소에서 조회할 수 있다. 조회에 실패하면 "실행 중일 수 있음"으로 보는 쪽이 안전하다.

## 결과와 위험

- **가용성은 보장하지 않는다.** 이 배포는 대회용 단일 호스트이며, 고가용성 구성이나 운영용 Temporal 구성이 아니다. 인스턴스가 멈추면 시연 전체가 멈춘다.
- **DB 마이그레이션은 자동으로 되돌리지 않는다.** 롤백은 코드만 이전 리비전으로 돌린다. 그래서 대회 기간에는 이전 코드와 호환되는 스키마 변경만 쓴다.
- **강제 배포는 실행 중인 이전을 취소한다.** 그래서 `force`는 명시적으로 켤 때만 동작한다. 취소된 이전이 원본 클러스터에 남긴 리소스는 데이터 이전 쪽 정리 절차로 확인한다.
- **API 교체 중에는 연결이 잠깐 끊길 수 있다.**
- **Worker 교체 시점.** 실제 Terraform Apply가 Worker에서 실행되면, 실행 중인 Apply를 확인하고 안전하게 Worker를 교체하는 절차가 추가로 필요하다. 지금의 실행 중 Workflow 확인이 이 경우도 막지만, Apply만 따로 기다리는 절차는 없다.

## 대안

구현 당시에는 대안을 비교한 기록이 남아 있지 않다. 아래 표는 이 ADR을 쓰면서 현재 구성과 비교해 정리한 것이다.

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| EKS나 ECS에 플랫폼을 올림 | 비용과 준비 시간이 늘어난다. 시연 대상 클러스터와 플랫폼 클러스터가 섞여 보일 수 있다 |
| Temporal Cloud 사용 | 계정과 인증서 준비가 필요하다. 시연에 필요한 규모에는 자체 Temporal로 충분하다 |
| 배포할 때마다 Worker를 graceful drain | Temporal Activity는 몇 분씩 걸리고, drain을 기다리는 동안에도 배포가 막힌다. 거절하고 사람이 판단하게 하는 쪽이 단순하다 |
| 작업 브랜치도 배포 허용 | 서버 상태를 main 기록으로 설명할 수 없게 된다. 꼭 필요할 때만 로컬 예외(`CMP_ALLOW_UNMERGED=1`)로 둔다 |
