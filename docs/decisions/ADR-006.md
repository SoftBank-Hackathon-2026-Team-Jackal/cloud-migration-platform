# ADR-006: 트래픽 전환은 Envoy 중계로 한다

- Status: Accepted — 팀 결정, 2026-11-05
- Tracking: Issue #61, #62, #63
- 기존 문서의 "Route 53 + Envoy 논의 중"을 대체한다.

## 결정

1. 점진적 트래픽 전환은 **Envoy 중계 서버**가 가중치로 수행한다(10 → 50 → 100%).
2. 각 단계는 통과 조건과 유지 시간을 모두 만족해야 올라간다. 실패 요청·p99 기준 초과, 설정 적용 미확인, 관측 불가는 모두 **원본 100%로 롤백**한다. 롤백 뒤 자동 재시도·자동 복귀는 하지 않는다.
3. 설정은 Envoy가 그 버전을 받아들였다고 확인된 뒤에만 성공으로 본다(RDS 파일 원자 교체 + 관리 API 확인).
4. P0 데모에는 자체 도메인이 없다. 사용자는 중계 서버 주소로 들어오며 가중치 100% 시점이 사실상의 전환이다. Route 53 DNS 최종 전환(`dns_finalize`)은 도메인이 생겼을 때의 확장이다. 중계 서버는 2026-11-07부터 `<공인IP>.sslip.io` 인증서(Let's Encrypt, 브라우저가 신뢰)로 HTTPS를 받는다(`infra/relay/setup-tls.sh`, 8080의 HTTP는 그대로). 보안 판정은 이 입구를 `보호됨`으로 본다.
5. DB 쓰기 주체가 대상이고 역방향 복제가 정상이라는 확인(DB 게이트)이 없으면 100% 단계는 막을 수 있어야 한다(`require_db_gate`). DB 전환 자체는 Data Migration 책임이다.
6. Provisioning 인계값이 `READY`이고 `ready=true`이며 `external_endpoint`가 있을 때만 실행한다. `UNKNOWN`은 확인 전에 진행하지 않는다.

## 실제 시험으로 정한 값 (2026-11-05)

플랫폼(Temporal 워커)을 통해 AWS 서울(원본) → GCP 서울(대상)로 실제 전환·롤백을 시험한 뒤 정했다.
- 새 연결의 1~2%가 연결 제한에 걸려 정상 상태에서도 503이 났다 → 라우트에 **연결 실패 재시도**(`connect-failure`, 2회)를 두고 연결 제한을 3초로 둔다(요청이 나가기 전 실패라 중복이 없다).
- 관찰 창 하나의 이상치(1초짜리 SYN 재전송 등)로 p99가 튀었다 → p99는 **창별로 판단하고 연속 2번 넘을 때만** 롤백한다. 실패 요청은 같은 단계 안에서 누적한다.
- Envoy의 JSON `interval` p99는 샘플이 적으면 비어 0으로 읽혔다 → **관찰 창 앞뒤 Prometheus 히스토그램 버킷 차이**로 창 p99를 계산한다.
- WAN 지연(대상 p99 73~130ms)이 더해지므로 p99 **절대 하한 기본 200ms**를 둔다.

## 중계 서버 + WireGuard 터널 시험 (2026-11-05)

AWS 서울 EC2(중계: Envoy + WireGuard 서버 `10.200.0.1`) ↔ GCP 서울 VM(온프레 역할: WireGuard 클라이언트 `10.200.0.2`, 앱 8080)으로 시험했다. 온프레 VM은 터널 안쪽 주소에만 앱을 열었고 인터넷에는 열지 않았다.
- 터널 MTU 1420에서 DF 핑 1392바이트 통과, 1393바이트 차단, 300KB 응답 정상. 터널 RTT 약 2.6ms(같은 서울 구간이라 WAN 지연 값은 아님).
- `external_endpoint=터널 IP`, `port=8080`(80 아님)으로 정상 전환 10→50→100 `DONE`. 5xx 주입·지연 주입·터널 단절 모두 원본 100% 롤백.
- 발견·수정: Activity마다 `EnvoyProxy`를 새로 만들어 라우트 번호가 항상 1에서 시작했다. Envoy가 이미 1을 보고하면 적용 확인이 곧바로 통과해 확인이 무의미했다 → 직전 번호와 현재 시각보다 큰 번호를 쓴다.
- 관찰: 컨트롤러(워커)와 Envoy가 다른 호스트면 라우트 파일을 원격으로 바꿔야 한다. 이번 시험은 시험용 접착제(SSH로 파일 교체)로 이었다. 이후 릴레이 워커(전용 큐)로 이 접착제를 대체하도록 구현했다(위 한계 항목).
- 한계: 온프레 K3s와 실제 Agent 연동, 폴링 API로 peer를 받아 오는 부분은 시험하지 못했다.

## 한계

- 중계 서버 한 대는 단일 장애점이다. HA는 설계만 하고 구현하지 않는다.
- 대상 주소는 이전이 넘긴 값(`external_endpoint`)으로 바꾼다: 대상 클러스터를 정적 설정에 박지 않고 파일(CDS)로 둔다. 릴레이 워커가 `traffic_prepare`에서 (동적으로 깔려 있고, 새 주소가 터널 대역(`TRAFFIC_TARGET_ALLOWED_CIDRS`) 안의 IP이고, 지금 대상 가중치가 0%일 때만) 주소를 바꾸고 Envoy에서 활성이 되는지 확인한다. 아니면 `TargetMismatch`로 멈춘다. 정적으로 깔린 중계 서버는 예전처럼 인계값과 다르면 멈춘다.
- 설정 배포는 Envoy와 같은 호스트에서 라우트 파일을 바꾸는 방식이다. 컨트롤러와 중계 서버가 다른 호스트면 중계 서버에 릴레이 워커(`cmp_worker.workers.relay`)를 띄우고 요청의 `relay_queue`로 그 큐를 지정한다(새 프로토콜 없이 파일이 로컬이 된다). xDS 서버는 필요해질 때까지 두지 않는다.
- 릴레이 워커 방식은 단위·재생 시험까지만 했고, 실제 중계 서버 호스트에서 돌려 보지는 않았다.
- WireGuard peer는 중계 서버가 플랫폼 `GET /relays/{relay_id}/agents`(Bearer = 중계 서버 등록 때 받은 자격증명)를 주기적으로 읽어 `wg set`으로 맞춘다(`python -m cmp_traffic.peers`). 응답 형식은 `docs/contracts/openapi.yaml`의 RelayAgentList(`list_version`, 폐기는 `revoked: true`)를 따른다. 단위 시험까지만 했고, 중계 서버를 플랫폼에 등록해 실제 목록을 받아 보는 시험은 남았다.
- 트래픽만 원본으로 되돌리는 것이 데이터 복구를 뜻하지는 않는다. DB 게이트로 보완한다.
- 사용자 트래픽이 없을 때(원본·대상 모두 관찰 창 요청이 `min_requests` 미만)는 "증거 없음"으로 롤백하지 않고, 중계 서버에서 대상으로 **합성 요청**(인계값의 헬스 경로로 읽기 전용 GET, 동시 5건)을 보내 실패·p99를 재고 평소와 같은 기준(`evaluate_step`)으로 판정한다. 통과하면 바로 다음 단계로 간다. 원본에 요청이 있는데 대상만 적으면 가중치가 안 먹었을 수 있어 해당하지 않는다(예전처럼 보류 후 롤백). 합성 요청은 대상이 허용 범위(터널 대역)의 IP이거나 중계 서버가 이미 그곳으로 보낼 때만 보낸다. 정책 `idle_probe`(기본 켬)로 끌 수 있다. 진행 중인 이전의 이력은 `workflow.patched("traffic-idle-probe-v1")`로 예전 흐름 그대로 재생한다.
- 롤백 사유는 `traffic.snapshot` 노트 `gateFail`의 `params`에 `kind`(p99·failed·requests)와 수치로 싣는다. 기준선(원본 p99)은 단계 시작 때 한 번 재고 재시도에서도 쓰므로, 그때 원본에 요청이 없으면 0이고 한계는 `p99_floor_ms`만 남는다.
- 실시간 연결(SSE 등)은 라우트 제한시간(5초)에 끊겨 `upstream_rq_timeout`으로 세어진다(실패 = 5xx + timeout). 그런 경로는 릴레이 워커 `TRAFFIC_STREAM_PREFIXES`(데모 `/api/stream`)로 지정해 같은 가중치로 나누되 제한시간 `0s`·재시도 없이 보낸다. 오래 열린 연결은 가중치가 바뀌어도 원래 쪽에 남고, 끊김·5xx만 판정에 들어간다([ticket 70](../../tickets/provisioning/70-relay-stream-routes.md)).

## 미정

- 중계 서버를 둘 위치(EKS Pod/노드, 별도 VM)와 전환 뒤 제거·인계 주체.
- 온프레미스 NAT 환경의 WireGuard 구성 세부(MTU 1420 고정은 실측 근거).
