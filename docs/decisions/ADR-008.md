# ADR-008: Sandbox 레드팀(능동 공격) 검증

- Status: Proposed — 사용자 결정 대기, 2026-11-07
- Tracking: Issue #332(티켓 33), #333(34), #334(35), #335(36)
- 관련: [ADR-002](./ADR-002.md), [ADR-004](./ADR-004.md)(비용 상한), [policies.md](../product/policies.md) P-04·P-10·P-12, [analysis-verification spec](../../specs/analysis-verification/spec.md) AV-023, [ticket 30 보안 프로브](../../tickets/analysis-verification/30-security-probes.md), [ticket 26 NetworkPolicy](../../tickets/provisioning/26-production-network-policy.md)

## 배경

Sandbox는 변환 오류를 찾고(§3), P-12는 원본·대상의 보안 설정을 비교한다. ticket 30은 시험 Pod로 "기본 차단 NetworkPolicy가 실제로 동작하는지"를 증명한다. 어느 것도 **배포된 앱을 실제로 공격해 취약점을 찾지는 않는다.**

목적: 격리된 Sandbox에서 배포 대상 앱 Pod만 공격해 취약점을 찾고, 사용자 피해를 줄이도록 수정 루프에 연결한다. 실제 운영 환경과 사용자 자원은 건드리지 않는다.

## 범위 구분

| 단계 | 바뀌는 것 | 성격 |
| --- | --- | --- |
| 1. 격리 | Sandbox Namespace의 레드팀 Pod·NetworkPolicy·Quota·보안 설정 | **배포 구성** |
| 2. 안전장치 | 증거 마스킹, 외부 차단, 데이터 초기화, 강제 확인 | 워커 코드 + 구성 |
| 3. 고정 도구·Finding | 도구 실행 Activity, Finding 계약 | 워커 코드 |
| 4. LLM 조율 | 기존 에이전트 런타임의 새 역할 | 워커 코드 |
| 5. 수정 연계 | `classify_failure`·Fixer 입력 | 워커 코드 |

Sandbox 밖(Production, Provisioning, Build)은 바꾸지 않는다.

## 결정

1. **소속·재사용.** Sandbox Worker의 확장이다. ticket 30의 시험 Pod 방식(고정 이미지, 비특권, 토큰·환경변수 없음, 모든 종료 경로에서 정리, 옵트인 설정 `SandboxSettings`)과 `cmp_providers.network_policy`를 재사용한다. 새 Worker·Task Queue는 만들지 않는다.
2. **실행기와 두뇌 분리.** 레드팀 Pod는 **허용된 고정 도구만 실행하는 실행기**다. LLM 판단은 기존 에이전트 런타임(08A, 마스킹, ADR-004 비용 상한) 안의 워커에서 하고, 워커가 Kubernetes API로 실행·결과 수집을 한다. Pod는 인터넷도 클러스터 API도 쓰지 않는다.
3. **통신: 앱 Service 하나만.** 레드팀 Pod에는 기본 차단 외에 앱 포트로의 egress만 허용한다. 공통 `allow_dns`는 Namespace 전체 Pod에 DNS를 열어 유출 통로가 되므로 **레드팀 Pod는 제외**하고(정책 선택자로 분리) 앱 주소는 IP로 주입한다. DB, 프록시, 다른 Pod, 다른 Namespace, 메타데이터(`169.254.169.254`), 클러스터 API는 모두 닫는다. 앱 쪽 수신은 기존 `entry` 정책이 포트 단위로 이미 연다.
4. **강제 확인(fail-closed).** 공격 전에 레드팀 Pod가 금지 대상(다른 Namespace Pod, 메타데이터 IP, 클러스터 API, DB)에 **닿지 않음**을 시험으로 확인한다. 하나라도 닿거나 확인할 수 없으면 `REDTEAM_ISOLATION_NOT_ENFORCED`로 중단하고 공격하지 않는다(ticket 26의 `NETWORK_POLICY_NOT_ENFORCED`와 같은 원칙).
5. **대상 한정.** 공격 대상은 `cmp.sandbox/run-id` 라벨이 붙은 Sandbox Namespace의 앱 Service뿐이다. 클러스터 식별자 allowlist와 라벨을 모두 확인한다. 소스 원본 환경, Production, 외부 호스트는 대상이 아니다. **대상 주소는 Agent나 도구의 인자가 아니라 워커가 Pod에 주입하는 고정값이다.** 도구 호출에는 호스트·URL 인자가 없고, 요청 경로(path)만 앱 안에서 고를 수 있다. 모델이 다른 주소를 요청해도 전달할 방법이 없으며, 네트워크(3번)와 외부 차단(6번)이 두 번째·세 번째 방어선이다. 범위 밖(외부 사이트 등)으로 나가려는 시도는 거절하고 기록한다.
6. **앱이 가진 실제 `.env`를 보호한다.** Sandbox 앱은 사용자의 실제 `.env`를 Secret으로 받는다(ENV-06). 그러므로
   - 공격 중에는 기존 `external_cut`으로 외부 egress를 끊어 실제 외부 서비스에 부수효과가 나지 않게 한다.
   - 요청·응답 증거는 저장 전에 `cmp_agents.masking`으로 마스킹하고, LLM에는 마스킹본만 보낸다.
   - Finding에 실제 키·토큰이 남으면 해당 Finding을 저장하지 않고 `SECRET_IN_EVIDENCE`로 표시한다.
7. **강도와 초기화.** 공격 강도는 3단계다: `PASSIVE`(관찰만), `ACTIVE`(앱 API 수준의 능동 시험), 제외(자원 고갈형 DoS·클러스터 부하). `ACTIVE`는 11B의 `snapshot_baseline` 이후에만 실행하고 끝나면 `reset_test_data`로 되돌린다. 기준선이 없으면 `ACTIVE`는 실행하지 않는다.
8. **Pod 자체 제한.** Namespace Pod Security `restricted`, `NET_RAW` 등 capability 전부 제거, `readOnlyRootFilesystem`, 서비스 어카운트 토큰 없음, digest 고정 도구 이미지(도구 템플릿·시그니처는 이미지에 포함, 런타임에 인터넷에서 받지 않는다), CPU·메모리·`activeDeadlineSeconds`, Namespace ResourceQuota와 동시 실행 상한을 둔다. 도구는 허용 목록으로 코드가 강제한다.
9. **옵트인과 실행 전 승인(R8).** 기본 꺼짐. 켜는 것(설정)과 실제 시작은 별개다. `PASSIVE`와 `ACTIVE` 모두 시작 직전에 사용자 승인 단계를 거치고, 승인 화면에는 대상(Sandbox 사본), 강도, 시간 상한, 데이터가 초기화된다는 점, 외부 통신이 끊긴다는 점을 보여 준다. 승인자·시각·강도·상한을 기록한다. 승인 대기 시간은 Sandbox 만료와 별개로 흐르므로 승인 시점에 남은 시간을 다시 확인한다(`REDTEAM_TIME_INSUFFICIENT`). 승인 방식은 기존 확정 Signal 게이트(08B·분석 검토 게이트)를 재사용하는 방향으로 하되, 실제 화면·API는 승인 화면 담당과 합의가 필요하다. 정책 문구는 P-13(R6)에 둔다.
10. **결과·Digest.** Finding(카테고리, 심각도, 재현 요청 요약, 마스킹 증거 참조)은 **이미지 Digest와 묶음 해시**와 함께 산출물로 저장한다. 수정 후 새 Digest에 같은 재현 요청을 다시 돌려 통과한 Digest만 P-10의 "검증된 Digest"가 된다.
11. **게이트.** 1차는 표시와 승인 기록까지다(D-17의 "약점은 표시와 승인 기록"과 같다). High 이상 미해결 시 승인 차단은 별도 결정(R3).
12. **수정 연계.** 수정 루프는 `classify_failure`에 보안 분류를 추가해 쓴다. 보안 수정과 기능 수정의 시도 횟수 상한 공유 여부는 R4에서 정한다. 수정이 보안 보호를 낮추면 거절한다(P-12).
13. **Workflow.** 외부 I/O는 Activity에서만 하고 Heartbeat와 재시도에 대비한다. Job 이름은 `run_id`·시도로 결정적이어서 재시도에서 Pod가 중복되지 않는다. 공격 시간은 Sandbox 만료(`expires-at`) 안에 들어와야 하며 넘으면 시작하지 않는다.
14. **입력은 그레이박스(R7).** Agent에는 앱의 경로 목록(메서드, 경로, 파라미터 이름)만 준다. 소스코드, `.env`, 비밀 값은 주지 않는다. 경로 목록은 분석 결과 또는 앱의 API 명세에서 가져오며, 분석이 라우트를 내는지는 확인되지 않았으므로 구현 전에 정한다. 의도적으로 취약하게 만든 데모 앱의 취약점 목록은 발견율을 재는 정답지로만 쓰고 Agent 입력이나 프롬프트에 넣지 않는다.
15. **데모 앱 노출 방지.** 의도적으로 취약한 앱은 가짜 데이터와 가짜 키만 쓴다. 승인 차단이 없는 1차 정책(R3)에서는 승인하면 취약한 이미지가 실제 대상(AWS/GCP/K3s)의 공개 주소로 올라갈 수 있으므로, 데모는 수정된 이미지만 배포하거나 취약 버전 배포 후 즉시 내리는 절차를 따른다.

## 남은 위험 (기록)

- **컨테이너 탈출(R5, 감수).** 같은 클러스터의 다른 Namespace와 노드를 공유한다. 컨테이너 런타임·커널 자체의 취약점으로 컨테이너 밖으로 나오면 NetworkPolicy는 막지 못하고, 같은 노드의 다른 Sandbox(소스·`.env` Secret)와 그 호스트에 있는 것에 닿을 수 있다. 가능성은 낮고(Pod 보안 설정 8번, 패치된 커널·런타임 전제), 감수한다. **감수 조건:** (1) Sandbox 호스트에 Production 자격 증명과 플랫폼 비밀(API·Temporal·DB·클라우드 역할)이 없다 — 단, 문서가 엇갈린다: ticket 58은 Sandbox k3d가 데모 EC2 안에 있다고 하고 ticket 45는 데모 서버에 없다고 한다. **사용자 확인(2026-11-07): Sandbox는 데모 서버와 같은 서버(EC2)에서 돈다.** 플랫폼(Docker Compose)과 Sandbox(k3d)는 서로 다른 컨테이너·Pod이지만 **같은 호스트의 커널을 공유**하므로 탈출 시 같은 서버의 플랫폼 컨테이너와 EC2 인스턴스 역할 자격 증명에 닿을 수 있다. 데모 한정으로 감수하되, 그 EC2의 인스턴스 역할은 최소 권한이어야 하고 `cmp-aws-prod` 같은 Production 수준 자격 증명을 두지 않는다. 사용자 확인(2026-11-07): 인스턴스 역할은 최소 권한이고 서버에 키는 없다고 본다(Claude는 서버에서 직접 검증하지 못했다). (2) 한 호스트에 서로 다른 사용자의 Sandbox를 동시에 두지 않는다(P0는 소유자 본인의 앱만; 사용자 확인: 동시에 올라오는 앱은 하나뿐이고 데모 한정이다). **재검토 조건:** 다른 사용자의 실제 앱·`.env`를 받기 시작할 때, 또는 Sandbox 호스트가 플랫폼과 같은 서버일 때.
- 실제 EKS·GKE Sandbox에서는 CNI 강제 여부가 다를 수 있다. 4번의 확인이 이를 잡는다.
- 사용자 앱이 인증서·외부 의존이 있어 외부를 끊으면 앱이 공격 전부터 실패할 수 있다. 이 경우 공격은 `SKIPPED`로 남긴다.

## 결정 기록 (2026-11-07)

사용자 확정: **R1** P0 범위에 포함한다 / **R2** `ACTIVE` 강도를 1차에 포함하고, 기존 11B의 `snapshot_baseline`·`reset_test_data`를 재사용한다(기준선이 없으면 `ACTIVE`는 실행하지 않는다) / **R3** 표시와 승인 기록만, 승인 차단 없음 / **R4** 보안 수정은 별도 시도 횟수 / **R6** P-13 신설 / **R7** Agent 입력은 그레이박스(앱 경로 목록: 메서드·경로·파라미터 이름. 소스·`.env`·비밀 값 제외)로 시작하고, 성공하면 고도화한다(블랙박스·소스 참조·도구 확대는 후속). 데모 앱에 심은 취약점 목록은 검증용 정답지로만 쓰고 Agent 입력에는 넣지 않는다. 의도적으로 취약한 앱이 실제 대상(AWS/GCP/K3s)에 공개 배포되지 않도록, 데모에서는 수정본을 배포하거나 취약 버전을 배포하지 않고 가짜 데이터만 쓴다. **R5** 현재 Sandbox 클러스터를 그대로 쓰고 잔여위험을 기록한다(전용 노드·샌드박스 런타임은 도입하지 않는다). 조건은 아래 "남은 위험"에 적는다.

R2 주의: 11B의 기준선은 DB 볼륨 안에 있어 DB가 재생성되면(`RECREATED`) 사라진다. 그 경로의 실제 클러스터 실행은 11B에서도 검증하지 못했다. 레드팀은 실행 직전에 기준선 존재를 확인하고, 없으면 새로 만든 뒤 시작하거나 `ACTIVE`를 건너뛴다.

**R7 (2026-11-07)** 1차는 **그레이박스**로 간다. 레드팀 입력은 앱 경로 목록(메서드·경로·파라미터 이름)과 마스킹된 요구사항·통신 의도뿐이고, 소스코드·`.env`·비밀 값은 주지 않는다. 데모 앱에 심어 둔 취약점 목록은 **검증용 정답지로만** 쓰고 Agent 입력에는 넣지 않는다. 1차가 성공하면 고도화하되, 고도화는 **입력 수준(그레이박스 → 다른 방식)을 바꾸는 것에 한정**한다. 시험 항목·공격 방식을 늘리거나 범용성을 넓히는 것은 이 ADR의 범위가 아니며, 필요해지면 새 ADR로 정한다. 경로 목록의 출처(분석 결과, 앱의 API 명세, 데모 앱 제공 목록)는 티켓 35 착수 때 확인한다.

R1 영향: P0 일정 안에 33·34는 필수, 35는 최소 범위, 36은 선택으로 본다. 범위 축소는 별도 합의로 한다.

아래 표의 "제안"은 위 확정으로 대체한다.
