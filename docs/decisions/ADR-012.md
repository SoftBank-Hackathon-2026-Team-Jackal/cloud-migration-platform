# ADR-012: 전환할 때 원본 앱의 NetworkPolicy는 허용 규칙을 더하기만 하고, 기존 정책은 고치거나 지우지 않는다

- Status: Accepted — 구현된 결정을 기록, 2026-11-08 (PR #375)
- Tracking: Issue #137, PR #375, [데이터 티켓 12-source-netpol-pgbouncer](../../tickets/data-migration/12-source-netpol-pgbouncer.md)
- 관련: [데이터 이전 명세](../../specs/data-migration/spec.md) DM-010·DM-015, [ADR-010](./ADR-010.md), [`infra/data-migration/source-prep/`](../../infra/data-migration/source-prep/README.md)

## 배경

`dm_route_app`은 원본 앱 Secret의 `DATABASE_URL`을 `cmp-pgbouncer:6432`로 바꾸고 앱을 재시작한다(ADR-010). 원본 EKS `chat-source`의 `chat-app-egress` NetworkPolicy는 채팅 앱 Pod의 외부 연결을 `chat-db:5432`와 DNS로만 허용한다.

2026-11-07에 이 문제를 먼저 찾았다(티켓 12-source-netpol-pgbouncer). 그때는 플랫폼 코드를 바꾸지 않고, 허용 정책 `cmp-allow-chat-app-to-cutover`를 원본 사전 준비로 손으로 적용했다. 이 티켓은 다른 원본 앱에도 정책을 자동으로 만들지는 결정이 필요하다고 남겼다.

2026-11-08 리허설에서도 같은 상황을 확인했다. 앱 Pod에서는 `cmp-pgbouncer:6432`로 가는 연결만 막혔고, PgBouncer, 터널, 대상 DB는 정상이었다. `route_app`의 `wait_service`는 `cmp-cutover` Pod에서 접속을 확인하므로, 앱 Pod에만 걸린 정책은 이 확인으로 잡을 수 없다. 그래서 플랫폼이 이 경우를 직접 처리하도록 했다(PR #375).

## 결정

1. `dm_route_app`은 앱을 재시작하기 전에 `_open_app_egress`(`apps/worker/src/cmp_worker/activities/data_cutover.py`)를 부른다. 이미 PgBouncer로 바꾼 뒤의 재시도에서도 다시 부른다.
2. `_open_app_egress`는 Deployment의 selector와 Pod 템플릿 라벨을 읽고, Namespace의 NetworkPolicy 목록으로 `egress_isolated`(`packages/data/src/cmp_data/cutover.py`)를 판정한다. 이 Pod를 고르는 Egress 정책이 하나라도 있으면 격리된 것으로 본다. `matchLabels`, `matchExpressions`(In, NotIn, Exists, DoesNotExist), 빈 selector, `policyTypes`를 생략한 정책(egress 규칙이 있을 때만 Egress로 봄)을 Kubernetes 규칙대로 다룬다.
3. 격리된 경우에만 `app_egress_policy`가 만든 `cmp-pgbouncer-egress`를 적용한다. 이 정책은 앱 Pod에서 `app.kubernetes.io/name=cmp-cutover` Pod의 6432/TCP로 나가는 연결만 허용한다.
4. 앱의 기존 NetworkPolicy는 고치지도 지우지도 않는다.

## 이유

- NetworkPolicy 허용 규칙은 합쳐진다. 정책을 하나 더하면 기존 허용(`chat-db:5432`, DNS)은 그대로 살아 있다(PR #375, `source-prep/README.md`). 기존 정책을 고칠 필요가 없다.
- egress 제한이 없던 앱에 새 Egress 정책을 무조건 만들면, 그 Pod를 고르는 정책이 생기는 순간 허용 목록에 없는 다른 외부 연결(DNS 포함)이 모두 막힌다. 그래서 이미 격리된 앱에만 만든다(명세 DM-015, PR #375).
- 티켓 12는 다른 원본 앱에도 쓰려면 정책을 플랫폼이 자동으로 만들지 정해야 한다고 남겼다. PR #375가 `route_app` 단계에서 자동으로 만드는 쪽으로 구현했다.

## 결과와 위험

- 원본 EKS에는 플랫폼이 만드는 것과 같은 정책(이름, 라벨, 내용 동일)이 이미 적용되어 있다. 이후 이전에서는 플랫폼이 같은 정책을 직접 만든다.
- 새 정책은 6432/TCP만 허용하고 DNS는 열지 않는다. 앱이 `cmp-pgbouncer` 이름을 해석하려면 기존 정책이 DNS를 허용해야 한다.
- 앱 Pod의 Egress만 다룬다. `cmp-cutover` Pod의 Ingress, PgBouncer에서 원본 DB로 가는 연결을 막는 정책은 판정하지 않는다. 티켓 12는 `chat-source`에 그런 정책이 없음을 확인했다.
- 판정은 `route_app` 때 한 번 한다. 그 뒤에 추가된 정책은 반영하지 않는다.
- `cmp-pgbouncer-egress`는 허용만 더하는 정책이라 남아 있어도 앱 동작에 영향이 없다. 이전이 끝난 뒤 함께 정리하는 기능은 후속 과제다.

## 대안(검토했거나 남겨 둔 것)

- 원본 앱의 기존 정책(`chat-app-egress`)에 6432 허용을 고쳐 넣기: 허용 규칙이 합쳐지므로 고칠 필요가 없어 쓰지 않았다(티켓 12, PR #375).
- 사전 준비로만 손으로 적용(`infra/data-migration/source-prep/`): 2026-11-07 방식이다. 매니페스트와 되돌리기 방법은 남겨 두었다.
- 격리 여부와 관계없이 항상 정책 만들기: 위 이유로 쓰지 않았다.
