# ADR-007: 온프레미스 대상 데이터 이전 경로는 원본 쪽 게이트웨이 입구(2안)로 한다

- Status: Accepted — 사용자 결정, 2026-11-07
- Tracking: Issue #288, [티켓 68](../../tickets/provisioning/68-onprem-data-path-decision.md)
- 바꾸는 문서: `specs/data-migration/spec.md` DM-011의 ON_PREM 문장(1안은 대안으로 남김)

## 문제

결선 데모 대상은 맥 k3d(온프레미스 K3s 역할)다. NAT 뒤에 있고 arm64다. 데이터 이전은 흉내나 가짜 데이터 없이 실제 PostgreSQL 논리 복제(초기 복사 + CDC + 전환·롤백)로 해야 한다. 기존 명세 DM-011은 ON_PREM에 "기존 Agent 터널(`tunnel_endpoint`)과 MNP Preflight를 쓴다"고만 적었고, 그 경로가 실제로 이어지는지는 확인하지 않았다.

## 확인된 사실 (2026-11-07, 코드·AWS 읽기 조회)

- 원본 EKS `cmp-demo-source`의 VPC는 `10.20.0.0/16`이다. 중계 서버·데모 서버는 `172.31.0.0/16`(기본 VPC)이다. 둘 사이에 VPC 피어링이 없다.
- Agent 터널(티켓 17)은 터널 IP에 앱 포트와 5432만 열고, 중계 서버(`10.200.0.1`)에서 온 연결만 받는다. 원본 DB에서 k3d로 가려면 중계 서버를 지나야 하는데, 중계 서버는 원본 VPC에 닿지 않는다.
- 데이터 게이트웨이(`packages/data/src/cmp_data/tunnel.py`, 데이터 티켓 10·11에서 EKS ↔ GKE 클라우드 검증)는 입구(UDP LoadBalancer)가 **대상 쪽**에 있고 원본 게이트웨이가 접속한다. NAT 뒤 k3d에는 공개 입구를 둘 수 없어 그대로는 못 쓴다.
- `packages/data/src/cmp_data/handoff.py`는 K3s 대상에 `target_kubeconfig_ref`가 있어야 한다(없으면 `TARGET_DB_ACCESS_UNSUPPORTED`). worker가 k3d Kubernetes API에 닿아야 한다(DM-001, `kubectl exec … psql`).

## 선택지

| 안 | 구성 | 장점 | 단점 |
| --- | --- | --- | --- |
| 1안(DM-011 원문) | Agent 터널 + 중계 서버 + 원본 VPC ↔ 중계 서버 VPC 피어링. 복제 데이터가 플랫폼 중계 서버를 지난다 | 새 입구가 없다. Agent 터널 하나로 앱·DB가 같이 간다 | 고객(원본) VPC에 피어링·라우팅 변경이 필요하다. 사용자 데이터가 플랫폼 인프라를 지난다. 중계 서버 장애가 트래픽과 데이터를 같이 멈춘다. 트래픽 담당 영역(중계 서버)에 데이터 전달 책임이 섞인다. 검증된 코드가 없다 |
| **2안(채택)** | 데이터 게이트웨이를 재사용하고 **입구 방향을 뒤집는다**: 원본 EKS에 UDP NLB 입구, 대상(k3d) 게이트웨이가 밖으로 접속한다. worker는 Agent 터널 + 중계 서버를 거친 kubeconfig로 k3d API에 접근한다 | EKS→GKE에서 검증된 코드·절차를 그대로 쓴다. 복제 데이터는 원본 ↔ 대상 직통이다. 고객 VPC 피어링이 없다 | 원본 쪽에 공개 UDP 입구가 생긴다. worker가 사용자 클러스터 kubeconfig를 가진다. EKS NLB UDP·NAT keepalive는 아직 실측 전 |

## 결정

2안으로 한다.

```text
원본 EKS (10.20.0.0/16)                                 맥 k3d (NAT 뒤)
 DB ◀─ gateway 10.210.0.1 ◀─ UDP NLB ◀── WireGuard UDP ── gateway 10.210.0.2 ─▶ DB
       (입구: 대상 공인 IP만 허용)              (대상이 밖으로 접속, keepalive 15초)

worker ──kubeconfig──▶ 중계 서버(TCP 전달) ── Agent 터널 ──▶ k3d API (좁힌 ServiceAccount)
```

이유:
1. **검증된 코드 재사용.** 게이트웨이 매니페스트·키 처리·`peer_host`·대상 DB 허용 정책은 EKS ↔ GKE 클라우드 검증(데이터 티켓 11)을 통과했다. 바뀌는 것은 입구 위치(어느 쪽에 LoadBalancer를 둘지)와 허용 대역뿐이다.
2. **데이터가 플랫폼 인프라를 거치지 않는다.** 중계 서버는 사용자 HTTP와 worker의 API 접근만 다룬다.
3. **고객 VPC 피어링이 필요 없다.** 원본 계정의 네트워크 변경은 Kubernetes Service(NLB) 하나다.
4. **장애 격리.** 중계 서버가 멈춰도 복제는 이어지고, 복제 경로가 막혀도 트래픽 경로는 그대로다.
5. **영역 경계.** 복제 경로는 데이터 담당 코드, 중계 서버는 트래픽 담당, Agent·kubeconfig 노출은 Provisioning으로 지금 담당 구분과 맞는다.

## 결과와 위험

- **worker가 사용자 클러스터 kubeconfig를 가진다.** 권한을 좁힌 ServiceAccount(대상 DB Namespace의 Pod `exec`·조회, `cmp-data-tunnel` Namespace 리소스 생성·삭제)로 만들고 cluster-admin을 쓰지 않는다. 토큰은 worker 설정(`DATA_MIGRATION_KUBECONFIG_DIR`)에만 두고 Workflow 입력·결과·로그에 남기지 않는다. 이전이 끝나면 지운다.
- **원본 쪽 공개 UDP 입구.** NLB는 대상 공인 IP(NAT 출구)에서 오는 51820/UDP만 받는다(`loadBalancerSourceRanges`). WireGuard는 키가 맞지 않는 패킷에 응답하지 않는다. 대상 공인 IP가 바뀌면 다시 설정해야 한다.
- **실측 전.** EKS NLB의 UDP 전달·헬스 확인, 가정용 NAT의 UDP 매핑 유지(keepalive 15초로 충분한지), arm64 게이트웨이 이미지. 단계 1 PoC(티켓 69)가 확인한다. 실패하면 이 ADR을 다시 연다.
- **MNP Preflight.** ON_PREM 복제 경로가 Agent 터널이 아니라 데이터 게이트웨이가 된다. Preflight 검사 위치(MNP-001 `probe_target`)는 대상 게이트웨이 경로여야 한다. 명세 변경은 단계 3·6에서 함께 정한다.
- 1안은 대안으로 남긴다. 고객이 원본에 공개 입구를 허용하지 않고 피어링을 허용하는 경우에 다시 본다.
