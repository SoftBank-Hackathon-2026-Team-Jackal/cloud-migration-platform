# ADR-003: Sandbox 검증 이미지 Digest를 Production에서 재사용

- Status: Accepted — 사용자·Sandbox 담당 논의 반영, 2026-11-03
- 구현 추적: [Issue #17](https://github.com/SoftBank-Hackathon-2026-Team-Jackal/cloud-migration-platform/issues/17), [B-01](../../tickets/provisioning/b-01-image-build.md)

## 결정

준비된 소스와 Dockerfile을 Sandbox 밖에서 빌드·Registry push하고, Sandbox가 그 이미지 Digest를 실행·검증한다. 실패 후 코드 수정이 있으면 새 Build를 호출하고 새 Digest로 다시 검증한다. 통과 시 **같은 Digest**를 Provisioning Plan·승인 산출물에 고정해 Production에서 재사용한다. 통과 후 재빌드하거나 태그를 다시 조회해 다른 이미지를 배포하지 않는다. 이 정책은 기존의 `Sandbox → 최종 Build` 순서를 대체한다.

민서가 맡는 공통 빌드 모듈은 Sandbox/변환 담당자로부터 **SHA-256 이름의 S3 소스 아카이브 URI 하나**를 받아 내려받기/검증/build/push하고 Digest 고정 이미지 참조·빌드 로그 위치·출처를 반환한다. Dockerfile과 빌드 컨텍스트는 아카이브 루트에 둔다. 작업/시도 ID·대상 플랫폼은 상위 실행 맥락, ECR 저장소·로그 버킷은 Builder 실행 설정에서 공급한다. Sandbox/변환 담당자는 소스 업로드·코드 수정·루프·빌드 모듈 호출·테스트와 통과 판정을 맡는다. 빌드 모듈은 Dockerfile을 자동 생성하거나 임의 언어/의존성의 오류를 수정하지 않는다.

이미지만 교체 가능한 시도는 같은 Chart에 새 Digest를 적용하고 재검증할 수 있다. 포트·환경변수·DB 스키마/데이터·자원 요구가 바뀌면 Values와 테스트 환경을 재평가하고, 필요한 경우 격리 리소스를 재구성한다. 이미지 동일성은 플랫폼별 실행·설정 동일성을 자동 증명하지 않는다. Sandbox가 실제로 실행한 플랫폼과 설정 범위를 결과에 남기고 Planning이 대상과 비교한다.

## 구현 전환

현재 내부 `PlanningRequest` v1은 `BuildResult.sandbox_ref`로 이전 순서를 표현하고, `SandboxResult`에는 검증 이미지 Digest가 없다. 이 코드/fixture는 새 정책을 아직 검증하지 못한다. B-01은 공통 빌드 모듈로 범위를 좁혔다. Build 선행 계약, Sandbox의 검증 Build 참조·Digest·플랫폼, `prepare_plan`의 동일성 검증과 최상위 Workflow 연결은 후속 통합 작업에서 구현한다. 구 v1 입력을 새 검증 증거로 자동 인정하지 않는다.

Build 실행 권한/Registry 접근, Digest 보존 기간과 멀티 플랫폼 manifest·플랫폼별 검증 증거는 B-01 착수 시 구체화한다. 빌드 시 런타임 `.env`·비밀값을 이미지/레이어/로그/Temporal 이력에 넣지 않는다.
