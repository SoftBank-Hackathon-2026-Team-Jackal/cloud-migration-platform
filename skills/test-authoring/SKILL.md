# test-authoring

## 언제 쓰는지
Tester가 소스를 읽고 앱을 검증할 테스트를 제안할 때 쓴다. 테스트의 기대값을 모델이 정하지 않고, 쓰기 모양(`shapes`)과 읽기 요청(`probes`)을 소스 근거와 함께 제안하는 방식이다.

## 조사 절차
1. "Routes found in the source"에서 데이터를 쓰는 경로(`POST`/`PUT`/`PATCH`)와 읽는 경로(`GET`)를 고른다. 같은 데이터를 다루는 쓰기·읽기 쌍을 찾는다.
2. `get_snippet`으로 핸들러 주변을 읽는다. 필요한 요청 본문 필드, 성공 상태 코드, 응답에서 서버가 만든 ID가 있는 위치를 확인한다.
3. 같은 키로 다시 쓰면 어떻게 답하는지 읽는다. 저장된 행을 돌려주면 `REPEAT_WRITE`, ID로 조회하는 경로가 있으면 `GET` 읽기를 쓴다. 둘 다 코드에서 확인되지 않으면 제안하지 않는다.
4. 읽기 전용 `GET`은 데이터베이스나 저장소의 내용을 돌려주는 경로를 고른다. 매번 달라지는 필드(시간, 생성 ID, 토큰)를 코드에서 확인해 `volatile`에 적는다.
5. 제안마다 `evidence`에 파일과 줄을 적는다. 그 줄에서 두 줄 이내에 호출하는 경로가 실제로 나와야 한다.

## 판단 기준
- 기대값을 직접 쓰지 않는다. 쓰기 모양의 값 필드는 `value-{{run_id}}` 그대로 두고, 읽기 요청의 답은 플랫폼이 기록한다.
- 근거를 읽지 못한 경로는 제안하지 않는다. 틀린 제안은 비용이 되고, 빠진 제안은 공백으로 기록될 뿐이다.
- 상태 코드만 보는 요청, 앱의 설정과 무관한 정적 응답, 외부 부수효과(메일, 결제, 외부 호출)가 있는 요청은 제외한다.
- 구현이 하는 대로 값을 베끼지 않는다. 코드의 상수나 계산 결과를 읽어 기대값으로 적는 것은 코드의 버그를 정답으로 만든다.

## 대상별 차이
- 대상(AWS, GCP, ON_PREM)이 달라도 테스트는 같다. 앱 API만 호출하므로 대상 환경은 요청 모양에 영향을 주지 않는다.

## 수정 패턴
- 이 역할은 코드를 수정하지 않는다. 수정은 Fixer가 하고, Tester는 Fixer가 무엇을 바꿨는지 보지 못한다.
- Tester는 첫 정상 기동 직후 한 번만 호출되어 거절 사유(`EVIDENCE_MISMATCH`, `RECORD_UNSTABLE` 등)를 받아 고칠 기회가 없다. 처음부터 근거 줄을 정확히 쓰고, 변동 필드를 빠뜨리지 않는다.

## 테스트 패턴
- 쓰기 후 같은 값이 읽히는지(왕복), 데이터베이스를 재시작한 뒤에도 같은 값이 남는지를 쓰기 모양으로 만든다.
- 목록·조회 경로는 `probes`로 제안해 응답을 기록하고, 이후 수정으로 응답이 달라지지 않는지 본다.
